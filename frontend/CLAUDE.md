# OIUEEI Frontend Documentation

React frontend using HDS (Helsinki Design System) from npm with OIUEEI customization layer (fonts, colors, icons). Vite dev server on `localhost:3000`. All API requests are proxied to the Django backend on `localhost:8000`. All UI strings are externalised via `react-i18next` (British English, `src/i18n/locales/en.json`).

The old `/collections/` is kept: the server answers it with a 301 to the right one, and in the app `useCanonicalCollectionPath(kind)` — called by `CollectionPage`, `ThingPage` and `JoinPage` — moves a visit made at the wrong prefix to the kind's (replacing the history entry, keeping the query, hash and state). ## Page Titles

Every page sets the tab's title through `useDocumentTitle(title)` (`src/hooks/useDocumentTitle.js`: it assigns `document.title` when the text changes and does nothing for an empty one). Dynamic pages (CollectionPage, ThingPage, UserPage, …) update it when data loads. Format: `{Page context} — OIUEEI` — `test/i18nParity.test.js` checks every `titles.*` string in the three locales ends with it.

For the previews chat apps build from a shared link (they run no JavaScript), the server fills the `<head>` of a public collection, a thing and a share link — and gives every other page the site's own card — before serving `index.html` (`core/services/link_preview.py`); React then sets the title as usual once it loads.

### Whose palette: the collection's, or the app's own

**The palette belongs to a collection, not to the reader.** Nothing about it is stored in the browser or chosen by whoever is looking. A page that belongs to a collection (`CollectionPage`, `ThingPage` and the thing pages read through a collection, `RequestThingPage`, `EditThingPage`, `DeleteThingPage`, `JoinPage`, `SharePage`, `AddThingPage`, `EditCollectionPage`, `CollectionAppearancePage`, `CollectionNotificationsPage`, `CollectionAvailabilityPage`, `DeleteCollectionPage`, `ManageInvitesPage`, `ImportInvitesPage`, `ImportThingsPage`, `RemoveGuestPage`, `LeaveCollectionPage`) **declares** the palette its API answer carries with `useCollectionTheeeme(colors, koro)` (`src/hooks/useCollectionTheeeme.js`, the same spirit as `useCollectionLanguage`): `theeeme_colors` + `koro` on the collection, `collection_theeeme_colors` + `collection_koro` on a thing, the share preview's. `useTheeeme()` — read by the page, `PageLayout`, the buttons — answers with the declared palette while that page is mounted and with **the app's own palette** everywhere else (Home, `/me`, `/me/edit`, `/me/data`, `/me/delete`, `/my-bookings`, `/owner-bookings`, `/new`, `/{kind}/new`, the login door, `/logout`, `/verify`, `/legal`, the contact page, the 404, the digest mute, the notification preferences and a deployment's own pages). The declaration is a small external store rather than a React context (equivalent: it needs no provider above any tree, which keeps every test and route simple), made in a **layout effect** so the app's colours never reach a frame, and withdrawn when the page unmounts (only if it is still that page's: a page mounted later keeps its own). `useTheeeme` takes no argument and reads no `localStorage`; `theeemeColors` and `koro` are removed once at start-up from browsers that still have them (`utils/retiredStorage.js`, called from `main.jsx` — **drop it a few releases after it ships**).

**A page that would paint its hero before it has its data waits for the answer** (a `LoadingSpinner` until then), or the app's palette would show for an instant: `JoinPage`, `SharePage`, `AddThingPage`, `ImportInvitesPage`, `ImportThingsPage` and `LeaveCollectionPage`. A collection that cannot be read (private, gone, a dropped connection) settles with no palette and the page keeps the app's, as the error views of the pages that already show a spinner do. `RemoveGuestPage` reads no collection: `ManageInvitesPage` hands it the palette in the navigation state. Pinned page by page in `test/collectionPagesPalette.test.jsx` (every page's hero wears **its** collection's colours, not the app's; no hero while the answer is pending) and the hook in `test/appPalette.test.jsx`; tests that need a palette in force declare it with `test/declarePalette.js`.

**The app's own palette (`Braaanding`)** is not HDS token names but six CSS variables of its own, `--color-braaanding-01` … `--color-braaanding-06`, and its map is `{color_01: 'braaanding-01', …, color_06: 'braaanding-06'}`, so the ~50 places that paint with `var(--color-<token>)` needed no change. The values are **hexadecimal and live in the database** (the `Braaanding` row, edited in the Django admin by whoever runs the deployment; the admin refuses a palette that fails the contrast the twelve meet). They arrive in the page the server hands out — `spa_index` writes `html:root{--color-braaanding-01:#…;…}` into the `<head>` (a block that outweighs the fallback whatever the order) and the koro into `<meta name="braaanding-koro">`, which `appKoro()` reads — so the first paint is right with no request. `src/styles/oiueei-theme.css` declares the seeded values in `:root` as the fallback for the Vite dev server (a backend test reads it against the migration's seed). Two readers of a token name needed more than the variable: the content link colour (`utils/linkColor.js` → `tokenHex`) resolves a `braaanding-0N` token to the hex the server wrote, and the **primary button's hover**, which for an HDS token is its `-dark` shade, has no derived shade for a free hexadecimal colour: the app's palette hovers to the hero pair (`color_03` fill with `color_05` label), the same as the emails' buttons. The 12 palettes are chosen by a curator on the collection's Appearance page; **the app's own is never in the selector**.

| `color_01` | Primary button background + secondary button border |

## Breakpoints

OIUEEI follows the official [HDS breakpoint tokens](https://hds.hel.fi/foundation/design-tokens/breakpoints/). HDS defines six; OIUEEI uses four and skips `breakpoint-s` (576px) and `breakpoint-xxl` (1440px). Use only these exact `min-width` values in media queries — never arbitrary pixel values.

| Token | Min-width | Container width | HDS grid columns | Margin |
|---|---|---|---|---|
| `breakpoint-xs` | 320px | 288px | 4 | 16px |
| `breakpoint-m` | 768px | 720px | 8 | 24px |
| `breakpoint-l` | 992px | 944px | 12 | 24px |
| `breakpoint-xl` | 1248px | 1200px | 12 | 24px |

The `page-container` and `form-hero-content` max-width is **1248px** (aligned with `breakpoint-xl`), and their side margin is `--page-margin`: **16px under 768px, 24px from it** (the Margin column above). The complementary `max-width: 767px` query (below `breakpoint-m`) is also valid for mobile-only overrides.

**Wide content scrolls inside itself, never the page body.** Since `hds-react@6.0.6` the `Table` container scrolls sideways by itself, with scroll shadows. Every HDS `Table` still sits in a **`.table-wrap`** (`overflow-x: auto`, App.css) — now a second container that never overflows, kept because it is the hook `ResponsiveTable` and `.responsive-table` hang from. `ManageInvitesPage` puts it on its table directly; the request tables and "My groups" get it through `ResponsiveTable`, which adds it on a desktop. **Below 768px those last three stop being tables and become a list of cards** (at ~100px a column, names broke word by word, status labels were cut off and the ✓ ⊗ buttons sat beyond the screen's edge). Markdown pipe tables in a bio have their own `.markdown-table-wrap` for the same reason. No `tabindex` on either: the rows carry links and buttons, so a keyboard reaches the off-screen columns by tabbing in. Those three pages' **actions column** (the row's buttons, no visible heading) carries a screen-reader-only header, `common.colActions` ("Actions") in a `.sr-only` span — HDS renders a non-sortable `headerName` as the `<th>`'s child, so a node works, and an empty `<th>` is an axe `empty-table-header`.

## PWA

The app ships a web app manifest (`public/manifest.webmanifest`) plus icons (`public/oiueei-icon-192.png` / `-512.png` — the orange O over the engel/bus koros split), so OIUEEI can be installed from the browser ("Add to Home Screen"). The `purpose: maskable` slot points at a **separate** `public/oiueei-icon-512-maskable.png`: the same art scaled to 80% inside the maskable safe zone with the two brand colours bled out to the edges, so an Android launcher masking to a circle/squircle keeps the whole logo; the plain `-512.png` stays full-bleed for `any` (and the 192 is the favicon/apple-touch source). `index.html` links the manifest, sets `theme-color`, and uses the 192px icon as favicon + `apple-touch-icon`. Colours are HDS tokens sampled from the icon: background `#ffe977` (engel), theme `#0000bf` (bus), the O `#fd4f00` (metro). In production Vite's `base: '/static/'` rewrites the `index.html` URLs and the manifest's icon `src`s are relative, so everything resolves under `/static/` via WhiteNoise. **No service worker** — installability only, no offline caching, deliberately minimal (DESIGN §7).

### LoginPage (`src/pages/LoginPage.jsx`)

- **API:** `POST /api/v1/auth/request-link/` with `{ email }` and the CSRF token, plus **`next`** when the URL is `/login?next=…` and `safeNextPath` accepts it (`{ email, next }`). `next` is the page the reader was on when their session ran out: `apiFetch` and `RequireAuth` put it there, the server keeps it on the RSVP and `VerifyPage` follows it back (see *Where a login returns to*).
- Standard `form-hero` + `Koros` layout with the app's own palette. **The hero title is the OIUEEI logo** (see "OIUEEI logo in the hero").
- **The door comes before the reading.** In order: the pitch (`login.pitch`) as an `<h2>`, the email form, the "new here?" button, the alpha warning, the explanatory paragraphs, and at the foot the deliberate-lookup link (the FAQ link when this deployment has one), which closes the page. The page has no `/legal` or `/contact` link of its own: the site footer, which sits on this same page, carries both (`appFrame.test.jsx` pins exactly one `/legal` link and one `/contact` link on `/login`, both inside the `footer`). `login.pitch` is two sentences naming the three kinds (a stall, a library of things, a shed) and the invitation; the licence paragraph below carries the EUPL half. A deployment's `deploymentI18n` that only overrides `login.operator` is unaffected.
- **The pitch is a heading, sized like body text**: `<h2 className="login-pitch">`, Body XL bold (20px/700, `.login-pitch`). Level and look are separate decisions: the hero's `<h1>` is the logo, so a lower-ranked heading would skip levels and axe's `heading-order` fires (verified by mutation).
- **A `?next=` line between the pitch and the form** (`login.nextNotice`, `.text-muted` inside `.measure`): when the login arrives with a valid `next`, one quiet sentence says why the reader is here ("Sign in and we'll take you straight to the page you were opening."). It deliberately does **not** say the session expired: the same line serves a stranger who opened something private. Absent without `next` or with one `safeNextPath` rejects; `LoginPage.test.jsx` pins when it shows and reads the words from `en.json`.
- **The alpha warning sits directly under the door** (`common.alphaNotice`, the sentence the FAQ and the legal notice carry): Body M bold in brick, `.login-alpha`, between the sign-in button and the prose, so nobody signs in without having met it. The shade is **`brick-dark`, not `brick`**, for contrast: at 16px this is normal text and owes 4.5:1, while plain brick reaches 3.94:1 on a `bus-medium-light` page background. `paletteContrast.test.js` reads size, weight and colour out of App.css and judges them **together**, re-deriving which WCAG threshold applies.
- A licence paragraph with a link to the GitHub repository (`login.licence`, rendered via `Trans` for the inline link) sits below the form.
- **Without an open door it says the instance works by invitation** (`login.inviteOnly`, a muted line where the "new here?" button would be): where `deployment/popInPath` is null — the standalone default — nobody can create an account from this page, and the server answers an unknown address exactly as a known one. The line stands before and after the email is sent; a deployment with a door shows its button instead. Pinned in `test/deployment.test.jsx` (the module mocked both ways).
- After submission the form is replaced by a `Notification`: `success` (the unified message; the backend returns 200 regardless of whether the email exists, for anti-enumeration) or `error` (server or network).

### VerifyPage (`src/pages/VerifyPage.jsx`)

- **API:** `GET /api/v1/auth/verify/{code}/` (resolve) on mount, `POST` of the same URL (commit a booking decision).
- **Booking accept/reject — one-click auto-commit:** when the GET returns `requires_confirmation` (a `BOOKING_ACCEPT`/`BOOKING_REJECT` preview, no mutation) the page **immediately fires the committing `POST`** from the load effect, showing "Verifying…" until it resolves to the success screen. The commit only runs from **real JS execution**: an email link-scanner or prefetch does a bare GET and can't decide a hold (the backend also refuses to commit on GET). A `committedRef` stops React 19 StrictMode's dev-only double effect from POSTing twice.
- **ACCOUNT_DELETE is the exception**: the GET preview renders a dedicated confirmation screen (account email, owned collection/thing counts, the what-stays line) and the POST only fires from the explicit **"Delete my account forever"** danger button, never from the load effect. On success it clears `userCode` from localStorage (the account has no palette to clear) and shows the goodbye screen (`verify.accountDeleted*`); Cancel exits to home/login.
- `COLLECTION_REJECT`: success `Notification` (the invitation was declined and the owner notified) and a "Go to login" button; no login/redirect.
- **On success** it stores `userCode` in `localStorage` (the account has no palette to store) **and applies the account's saved language** — `data.user.language`, if one of `SUPPORTED_LANGUAGES`, with `await i18n.changeLanguage(...)` **before navigating**, persisted like the profile's own Select (`App.jsx`'s mount effect runs once, before there is a session). Empty ("Automatic") or unknown ⇒ untouched; a failed language load never fails the sign-in. **The verify effect does not depend on `t`**: a language change gives a new `t`, and an effect that redeems a single-use link must not run twice. Auth tokens are HttpOnly cookies set by the backend. **The destination comes from the backend's `landing` field** (`core/views/CLAUDE.md` → VerifyLinkView): `collection` ⇒ `/collections/{data.collection || data.invited_collection}`, **`path` ⇒ `data.path`** (the page the login was asked from, `next`; re-checked with `safeNextPath` because it is handed to the router, and one that fails falls through to `/`), anything else ⇒ `/` (an unknown landing just goes home).
- On failure: error `Notification` with guidance and a "Go to login" button. **A 403 carrying `code: "no_longer_manages"`**: a co-curator demoted after the email pressed the old link; the server refused, burnt the link and left the request pending, and the page says `verify.noLongerManages` with **no** `expiredHelp` line. **A refusal carrying `retryable`** (an approval blocked by the invitation quota or the member ceiling) leaves the link working: the page shows the server's own reason and `verify.refusalHelp` ("this link still works") instead of `verify.invalidOrExpired` + `expiredHelp`. **A refusal carrying `code: "invite_already_asked"`** (the suggested person was already invited by email: the suggestion stays pending for a curator to decline, but the block lasts a year) shows `requestErrors.invite_already_asked` in the reader's language and, like `no_longer_manages`, **no** help line at all (the shared `reasonOnly` state). Every other refusal consumes its RSVP, which is why the expiry copy is right for them.

### HomePage (`src/pages/HomePage.jsx`)

- **APIs:** `GET /api/v1/auth/me/`, `GET /api/v1/collections/`, `GET /api/v1/invited-collections/`, `GET /api/v1/my-invitations/` (HttpOnly cookies). **`/collections/` is paginated and read to the last page** (`utils/fetchAllPages.js`, `?page_size=100`, following `next`): a later page that fails leaves the groups already read under the section error. `/invited-collections/` is not paginated (a plain list). Redirects to `/login` if no `userCode` in `localStorage`; stores `userCode` there on a successful fetch.
- Greeting and a button row holding **one** button: "Create collection" (`/new`, primary), the only thing Home offers that the account menu does not ("My profile", "My requests", "Requests to me", "Edit profile" and "Log out" live in the account menu). **It is in one place only:** with any collection of their own, active or not, it is in the hero and "My collections" below is just the list (all inactive: `userPage.noCollections` and the inactive list, no button); with **no collection at all** the hero has no button and "Create your first collection" under "My collections" is the invitation; while the collections read is in flight there is no button yet, and if it fails the hero's is the one that shows. Pinned in `HomePage.test.jsx`.
- **Inbox notifications**: `<InboxNotifications />` bare (every notification the user has — see Shared Components). It gets `onNetworkError` (its failed fetch feeds the offline banner like the four dashboard fetches) and `reloadKey`, bumped by `reloadDashboard()` so a Retry / a returning connection re-fetches the inbox too.
- **Pending invitations**: one dismissible HDS `Notification` (`info`) per pending invite, above the collections: the owner name as label, the collection headline in bold, and two `ButtonLink`s in a `.button-row-wide` — **"Accept invitation" primary and first** (`btnStyle`, `/verify/{accept_code}`) and **"Decline invitation" secondary** (`btnSecondaryStyle`, `/verify/{reject_code}`). Dismissing removes it from local state only (the RSVP remains until acted on). Pinned in `HomePage.test.jsx` (order, tokens, the `hds-button` class, the wide row, a pair per invitation); not seen on a phone.
- **My collections**: own ACTIVE collections as `CollectionLinkbox` rows (`collections-grid` — a vertical stack of image-less, full-width rows at every breakpoint). Each row shows the headline and, under it, the kind and the counts — "Library · 3 things · 5 members" (`kinds.<K>.short`, then `userPage.thingsCount`/`membersCount`, pluralised: "1 thing · 1 member"); a collection read without its `kind` shows only the counts. The empty state links to `/new` plus a second **"See how it works"** button that follows `deployment/aboutPath` and is **absent upstream** (`deployment.test.jsx` pins both halves).
- **Inactive collections**: below My collections when at least one own INACTIVE collection exists.
- **Shared with me**: invited ACTIVE collections as `CollectionLinkbox` rows, **minus the ones the account helps run** (`is_curator`): a co-curator is always on the invite list too, so the group came back from both reads; it stays under My collections only. Filtered on Home, not in `/invited-collections/`, because the profile's "My groups" reads the same list. Empty state: a no-shared message.
- **Section order follows what the account has**: once the dashboard knows the user **owns no collection and belongs to at least one group** (`groupsFirst`), "Shared with me" leads and "My collections" follows it (most such accounts arrived through somebody else's group, and an empty section with a create call would put the one thing they have below the fold on a phone). Anyone who runs a collection, and a brand-new account, keep the usual order. Pinned in `HomePage.test.jsx`.
- **Failure states are tested** in `HomePage.test.jsx`: a dropped connection (a fetch rejecting with a `TypeError`) shows the "Connection problem" banner and Retry brings the dashboard back; the browser's `online` event does the same without a click; the inbox failing raises the same banner over a page that loaded; a section the server *refused* (an HTTP error) says so inline, leaves the other section alone and Retry re-runs the dashboard; dismissing one invitation removes that one only; INACTIVE collections sit apart, after the active ones, under their own heading. (A coverage note: a number that moves with which files ran is a sign of behaviour with no test, not of a race — V8 can count an uncalled inner function as run when worker results merge.)
- **Feedback button**: `<FeedbackLink style={btnSecondaryStyle} />` at the foot of the content, alone and secondary, in a `.button-row-wide.feedback-link`. The container exists even when the deployment has no feedback URL, so `App.css` hides an empty one (`.feedback-link:empty`, hence the class on the row itself).

### CollectionPage (`src/pages/CollectionPage.jsx`)

- **API:** `GET /api/v1/collections/{code}/`. Handles 403 and 404 with specific messages.
- **The page loads and holds the collection; three blocks of it are components** (`src/components/collection/`), each owning the state only it uses: `CollectionHero` (the corner of menus, title, team line, the buttons of each kind of reader, the signed-in visitor's join), `ThingsSection` (tag chips, the grid with its 24-card "Show more", the empty messages; `InactiveThings` is the second grid) and `BroadcastBox` (a curator's message to the group). The page keeps the fetch, the added-thing arrival, the notices between hero and grid, and the two stable callbacks it hands to the cards (`handleUpdateThing`, `reloadCollection`).
- **Hero logo:** with `collection.thumbnail_url` the image is the collection's **logo**, not a backdrop: an ordinary `<img class="hero-logo" alt="">` (the `<h1>` already names the collection) placed after the back link and before the title, in a hero that carries `form-hero--collection` and never `form-hero--photo` or `HeroPhoto`. Its width is **one column of the card grid** (`--grid-column`, from `--grid-columns` 1/2/3/4 at the HDS breakpoints and the page margin — 288, 348, 298.66 and 282px at 320, 768, 992 and 1248) and its height is whatever its proportion gives (`height: auto`, no `object-fit`): never cropped or stretched. **Under 992px** it opens the content on the left, with G under it (the hero's rhythm); **from 992px** it floats right — the last column, its top edge level with the title's (the title beside it has no margin above) — and the hero holds it (`display: flow-root`). **The collection hero's text keeps to the columns before it** from 992px (`max-width` of columns − 1 columns and their gaps: 621.33 at 992, 894 at 1248), logo or not, so it never runs under it. `form-hero--photo` and its `padding-right: 34%` rule stay for `UserPage` alone: `JoinPage` and `EntityPage` paint the image the same way, through `PageLayout`'s `logoUrl` (`form-hero form-hero--collection`, `<img class="hero-logo" alt="">` after the back link and before the `<h1>`), reusing these rules unchanged. Pinned in `test/collectionLogo.test.jsx` (the stylesheet) and `CollectionPage.test.jsx` (the DOM); jsdom paints nothing, so the pixels are for a browser at 320, 768, 992 and 1248. No thumbnail ⇒ plain hero.
- **Hero back link** always reads "← Home" (`common.home`), but its **destination is the group's own `home_page` when the owner has set one** and the app's home (`<Link to="/">`) otherwise. When `home_page` is set and `sanitizeUrl` accepts it (http/https only) `BackLink` gets an `href` and renders a plain external `<a rel="noopener noreferrer">` in the same tab; a non-http value falls back to the internal link. A link named "Home" that leaves the site is a fair surprise for a screen-reader user — a known cost of keeping the two looking alike. Pinned by `CollectionPage back link says Home wherever it goes` (target and `rel` per case, exactly one icon, the raw i18n key).
- **`isCurator`, not client-side `isOwner`, gates every admin control**: the server-computed `collection.is_curator` (owner **or** co-owner) is the one field that says who may act. The page derives a strict `isOwner` (`userCode === collection.owner`) only for the founder-only pieces (the attribution line).
- **The curator's hero row** (owner or co-owner): **`[Add thing]` first and primary** (`/collections/{code}/add`; what a curator does most and an empty group needs first), and **always a second button, secondary, `[Invite your people]`** (`collectionPage.inviteYourPeople`) to `/collections/{code}/invites` — with things or without, members or without, so the row keeps its one primary. Editing the group is not in the row: it is "General" in the pencil menu (`CollectionSettingsMenu`), the only link to `/edit` on the page. A member, a dinamizador of a network and a reader with no session have neither the pencil nor that link. "Add thing" is also in the collection menu (deliberately repeated). Pinned in `test/inviteYourPeople.test.jsx` (two buttons in order with their `href`s and tokens in every shape of the group, curators only) and `CollectionPage.test.jsx` (no link to `/edit` outside the pencil menu).

### RequestThingPage (`src/pages/RequestThingPage.jsx`)

- **APIs:** `GET /api/v1/things/{thingCode}/` (**with `?collection={code}` on the collection-context route**, so the rules the form is built from are that collection's — the same one the POST names in `collection_code`; see `ThingSerializer` in `core/serializers/CLAUDE.md`), `GET /api/v1/things/{thingCode}/calendar/` (blocked periods for date-based types), `POST /api/v1/things/{thingCode}/request/`. At `/collections/:code/things/:thingCode/request` or `/things/:thingCode/request`; redirects to `/login` if no `userCode`.
- **The page is the frame and the booking logic; each way of asking is a component** (`src/components/request/`): `ConstrainedRentalFields` (a loan or rental with fixed lengths), `FreeRentalFields` (pickup and return dates), `DayReservationFields` and `HourlyReservationFields` (a reservation by the day or by the hour), plus `RequestSuccess` and `JoinGroupNudge`. The state of the day → duration → start-time choice is `useHourlyReservation` (`src/hooks/`), handed to `HourlyReservationFields`; the project note is passed as `children`, since it sits inside each reservation block. The page keeps what every flow shares: the thing, the dates, the calendar, `buildReservationBody` and the submit.
- **Back link**: `location.state.backPath` / `backLabel` from `ThingLinkbox` or `ThingPage`. **Page title**: `Hold: {thing.headline}` with the fee when present.
- **The collection's request-page note**: a Markdown note the owner writes once for the whole collection (`Collection.request_info`, the Availability page), shown for **every** date-based verb reaching this page (LEND/RENT/RESERVE). Read via `thing.collection_request_info` (resolved through `useLocalized`'s `L`) and passed as `PageLayout`'s `description`, rendered through `<MarkdownText>` — `PageLayout` renders `description` in a `<div className="form-hero-text">`, not a `<p>`, so Markdown's block output (lists, headings) is legal. Absent when the collection has no note.
- **Form fields** by type:
  - `LEND_THING`, `RENT_THING` — `DateInput`s for start and end with blocked-date validation. **In its free form (no fixed lengths) the two pickers follow the server's rules: the collection's weekdays and the chained handovers** (`freePickupDisabled` / `freeReturnDisabled` in `utils/rental.js`): a booking `[s, e]` occupies the pickup on `[s, e)` and its return day `e` is free for the next pickup, and a request `[start, end]` conflicts only if it shares an interior day with a booking (`BookingPeriod.has_overlap`: `s < end AND e > start`, the same strictness as `compute_availability` and the card's "available from …"). So the **pickup** picker is out on `[s, e)` of every booking and on closure days; the **return** picker is judged against the pickup chosen so far — out before the pickup, out on a closure day, and out when the stretch `[pickup, return)` runs over a booking (`rangeBlocked`, where touching a booking's pickup is a chained handover and stays open); the pickup's own day is a same-day return; with no pickup yet the return follows the pickup's rule. **The weekdays**: both helpers take `rentalWeekdays` (the collection's `rental_weekdays`, Python's 0 = Monday, `[]` = any day) and a day of a weekday that is not allowed is out in **both** pickers (the server demands them at both ends, with or without fixed lengths: `Collection.rental_violation`, `rental_pickup_weekday` / `rental_return_weekday`). The two rules add up: a Saturday that a booking occupies is still out, and its return day (a Saturday too) is still the chained handover. No client-side overlap check exists at submit; the server's 409 stands. Pinned in `utils/rental.test.js` and `test/requestRental.test.jsx` (the real HDS calendars, a 06→08 request after a 05→06 booking, a "Saturdays only" collection in both calendars). **Rental rules:** when the thing's collection defines `rental_durations` (from `ThingSerializer`), the free pickers are replaced by a **duration `Select`** (the collection's fixed lengths) + a single **pickup `DateInput`**; the return date is derived (`pickup + length`, shown as "Return by …" — a one-week rental picked up on a Wednesday returns the NEXT Wednesday, so a single allowed weekday stays satisfiable). The pickup picker (`isPickupDisabled`) disables days whose weekday — or the computed return day's — isn't in `rental_weekdays`, and any day whose range overlaps a booking. The request POSTs `collection_code` so the backend applies the right collection's rules. With a **single** fixed length it is preselected so the pickup picker is usable straight away.
  - `RESERVE_THING` — **two flows, chosen by `thing.reservation_unit`, never both.**
    - **`DAY`** — **pickup date + duration in days** (1..`thing.reservation_max_days`; the duration `Select` is omitted and the length fixed to 1 when the cap is 1) plus an optional **`project_note` `TextArea`** (≤512). A duration's label (`RequestThingPage.jsx`'s `durationOptionLabel` — `reservation.minutes`/`hours`/`hoursAndMinutes`) reuses the plain-hour key on a whole hour. Picking a new day resets both radios; a new duration resets the start-time one. **A Reserve click still missing a duration or a start time says so**: the incomplete group shows HDS's `errorText` (`rental.durationRequired` / `reservation.startTimeRequired`) and focus moves to its first option, which is what a screen reader hears (HDS accessibility bug 7). A start is only "missing" when there were some to choose. POSTs `{ start_date, start_time, end_time, project_note, collection_code }` — `end_time` is derived client-side (`formatHM(parseHM(start_time) + duration.minutes)`), never sent as a duration. **Once all three parts are picked, a `reservation.slotSummary` line shows the whole slot** ("Reserved on 03/06/2026, from 11:00 to 13:00.") inside the same `StatusRegion` as the "no start times" notice.

Accepts an ISO date, an ISO datetime or a `Date`; `''` for anything unparseable (never "Invalid Date"). Backend emails match it via `email_service._fmt_date`.

## Shared Modules

### API Service (`src/services/api.js`)

- `apiFetch(url, options)` — Centralised fetch wrapper. `credentials: 'include'` for cookie-based auth, `Content-Type: application/json` for requests with a body. On 401 it silently attempts a token refresh via `POST /api/v1/auth/refresh/`; when the session is gone for good it clears `userCode` and redirects to **`loginPathFor(window.location)`** — `/login?next=<the page>` — in both places it can (refresh refused, or refresh accepted and the retry still 401; each has its own test). Only `userCode` is stored in localStorage (for ownership checks).
- **`apiErrorMessage(data)` / `extractApiError(res)`** give the best user-facing message from a failed response: a coded refusal (`{code, params}`) is looked up in `requestErrors.<code>` first (`codedErrorMessage`, `params` interpolated, the number doubling as the plural count), then `detail`, `error`, `non_field_errors[0]`, the first field error. The server lifts a known validation refusal's code to the top of the body (`CODED_VALIDATION_REFUSALS`), so a DRF error is said in the reader's language too; a code this client doesn't know falls back to the server's English sentence. A 429 has no useful body: callers map it to `common.tooManyAttempts` first.

### Where a login returns to (`src/utils/nextPath.js`)

The refresh token lasts 7 days; after that any protected page 401s and the reader is sent to `/login`. The redirect remembers the page so that the magic link they ask for brings them back to it (every email link — a decision notice, a question to answer, the digest — names a page):

- **`safeNextPath(value)`** returns the value if it is a same-site path, else `''`. The rules are the server's (`core.utils.safe_next_path`, the gate — this copy is defence in depth): at most 256 characters matching `^/[A-Za-z0-9/_\-.~?=&%]*$`, not starting with `//`, no `..` (raw or percent-decoded), not `/` alone, not starting at `login`, `logout`, `verify`, `rsvp` or `magic-link` (decoded, case-folded). `src/test/nextPathParity.json` is read by `nextPath.test.js` and by the backend's test, so they cannot drift. The percent-decoding is byte-wise and never throws (the whitelist allows a lone `%`, and `decodeURIComponent` does not).
- **`loginPathFor({ pathname, search })`** is `/login?next=<encoded path+query>`, or plain `/login` when `safeNextPath` says there is nowhere to come back to. Used by `apiFetch`, `RequireAuth` (`<Navigate to={loginPathFor(location)} replace />`) and the signed-out `AccountMenu` link.
- **`isDoorPath(pathname)`** — whether a path is one of the SPA's own doors (`/login`, `/logout`, `/verify/…`, `/rsvp/…`, `/magic-link/…`; decoded, case-folded, query ignored): the list `safeNextPath` refuses, so the two cannot disagree; the signed-out `AccountMenu` paints nothing there.
- `LoginPage` reads `next` (`useSearchParams`) and sends it in the `request-link` body; the server stores it on the RSVP and `VerifyPage` follows `landing: "path"`. **`next` never touches the browser's storage, on purpose**: the magic link is often opened in another browser (Gmail's web view, the phone's mail app) that shares nothing with the one that showed `/login`, so the server-side RSVP is what crosses that gap (and the README's storage-key inventory, which `browserStorage.test.jsx` guards, is unchanged).

### File downloads (`src/utils/downloadBlob.js`)

`downloadBlob(blob, filename)` hands an already-fetched `Blob` to the browser as a download. There is no declarative way (a `<a download>` needs a URL that exists only after the response), so it is imperative DOM, and both ways a copy drifts are invisible in the happy path: an object URL never revoked pins the blob in memory for the life of the tab, and an anchor left in the body is a stray focusable element. **The caller keeps the request and its failure copy** (what a 429 says differs per page). Used by `useCollectionDownloads`, `useCalendarExport`, `DataExportPage` and anything else that offers a file. `filenameFromResponse(res, fallback)` reads the `Content-Disposition` filename off a response, or `fallback`: shared so the two data-export downloads (`DataExportPage` and the collection menu's JSON) read the server-set `oiueei-{code}-{date}.json` identically; the stats CSV builds its own name (`{code}-stats.csv`), since that endpoint never set the header.

### Owner content in one text per language (`src/utils/localized.js`)

The mirror of `core/utils.py::parse_localized` / `resolve_localized` — it must **stay** a mirror: if the two sides disagreed on what counts as a map, a card would show raw braces for content whose email reads as words. `parseLocalized(value)` returns the `{lang: text}` map or `null` (strict: a JSON object, keys ⊆ `es`/`ca`/`en`, all values non-empty strings — anything else is prose and renders verbatim). `localizedText(value, lang)` resolves it (`lang` → `es` → the first language written, so nobody faces JSON), and **`useLocalized()`** binds it to the reader's language — the twin of the email service's `L`:

```jsx
const L = useLocalized();
<h1>{L(thing.headline)}</h1>
```

Every site that renders owner content calls it: `ThingLinkbox`, `ThingPage`, `CollectionLinkbox`, `CollectionPage` (which resolves once and hands the words to its children — cards, share menu, back labels, **and its tag-filter chips**: the raw string stays the filter key, only the label resolves), `HomePage` (inbox payloads + pending invitations), `MyBookingsPage`, `OwnerBookingsList`, `RequestThingPage`, the delete/leave confirms, `ThingTags` and the tag pickers, plus every `document.title`. **The edit forms are the exception**: they show the *raw* value, because that is what the owner is editing (only their title and back label resolve). `localizedCounter(value, limit)` is the form counter: `18/64` for plain text, `es 18/64 · ca 17/64` for a map (each language gets the whole limit, the rule the server enforces), plus an `over` flag the forms turn into an inline error; it also reports `unreadMap` when the text **opens like a map** (`{`, after any spaces) **and is not one** (a missing quote, a trailing comma, an unread language code), and **`localizedHelper(value, limit, t)`** is the helper line every such field shows: the counter plus, in that case only, `localized.readAsPlain` ("Read as plain text — to write one per language, check the quotes and the codes es, ca, en."). Prose that starts any other way never trips it. Used for the thing's headline and description (`ThingForm`), the collection's headline, description, request note (Availability), email note (Notifications) and the deposit policy (Availability); pinned in `utils/localized.test.js`, `test/thingForm.test.jsx` and `test/collectionForm.test.jsx`.

### Errors that follow the language (`src/utils/errorKey.js`)

A page that shows an error it raised itself holds it as `errorKey('some.key', { params })` and paints it with `translateError(t, error)`, so a language switch with the error on screen re-words it (`setError(t('x'))` kept the sentence of the language current when it failed). A plain string is left as is: it is text the server wrote (a refusal's reason, `data.error`, `extractApiError`), which has no key. Used by the contact, data-export, delete-account, verify, share and profile pages and the upload, tag, opening-hours, CSV and gallery fields; pinned in `test/errorsFollowLanguage.test.jsx`. `CollectionPage` and `ThingPage` already held a plain key and translate at paint. Not covered: `LoginPage`'s `setMessage(t(…))` and `VerifyPage`'s `setSuccess`/`setTitle`, which are not errors.

### Custom Hooks

- **`useThingBooking`** (`src/hooks/useThingBooking.js`) — The lower-level booking **engine**: owns the reservation state, the owner-calendar fetch (`AbortController`-guarded, re-runs by `thing.code`) and the three async handlers (`handleRequest`, `handleActivate`, `handleBookingAction`). **A `403` on accept/reject is its own message**: the server refusing a decision means this reader no longer runs the thing (a co-curator demoted in another tab whose card still offers the buttons), so `handleBookingAction` says `thingPage.noLongerDecides` and **reloads the thing** (`GET /things/{code}/`, through the collection when there is one) into the parent via `onThingChange`, so the controls that are no longer theirs disappear; if the reload fails the generic `errorConfirmingHold`/`errorCancellingHold` stands. Both `ThingLinkbox` and `ThingPage` go through it; the card-vs-page differences are options (`initialActivePending`, `initialRequested`, `fetchOnEndless`, `bookingKeepsStatus`, `activateSuccessMessage`). **`collectionCode`** is sent in the request POST body: it names the collection the requester was browsing, which is where the owner's notification appears (`ThingLinkbox` passes its `collectionCode` or `thing.collection_code`, `ThingPage` the code it uses for login-to-act; the standalone page has none and the backend approximates; `RequestThingPage` posts it for the rental rules too). Returns `{ submitting, requested, bookingAction, bookingActionVerb, activating, bookings, activePendingCode, handleRequest, handleActivate, handleBookingAction }`.
- **`useThingActions`** (`src/hooks/useThingActions.js`) — The **view-model** wrapping `useThingBooking`, shared by `ThingLinkbox` and `ThingPage` so the owner-button matrix and reserve-button logic live in one place. Derives the type flags (`isOwner`, **`canManage`** — `thing.can_manage`, floor `isOwner`; the matrix, `canDelete` and the `!canManage` reserve-button guard key on it — `isCollectionOwner`, `isDateBased`, `needsPage`, `canDelete`, `hasPendingBookings`) and the reserve button's `showButton` / `buttonDisabled` / `loginButtonDisabled` / `buttonLabel`, plus everything `useThingBooking` returns. `canManage` also gates the owner-calendar fetch (the backend serves the requester-detail calendar + embedded `bookings` to a manager). The genuine differences are options: `isPaused` (card on a paused collection; the page passes false), `canAct` (the page passes `isAuthenticated`), `loginToAct` (anonymous-on-public — buttons show but each click routes to `/collections/:code/join`), `collectionOwner`, `collectionCode`, and the `useThingBooking` seeds. `bookingKeepsStatus` (`needsPage || is_endless`) is derived here. `useThingActions(thing, userCode, options)`.
- **`useCapabilities`** (`src/hooks/useCapabilities.js`) — What this deployment lets the signed-in account create: the `capabilities` block on `GET /auth/me/` (`{collection_modes, collection_kinds, thing_types, request_url}` — see `core/services/CLAUDE.md`). One request per signed-in account, shared by every form that asks and keyed by `userCode` so it cannot outlive a logout. **Null until known and null on failure**; every caller reads null as "no restriction" and offers the whole catalogue — a courtesy to the user, never the gate (the server refuses regardless). **A failure is not cached** (a non-OK status counts as one): failing open is deliberate, remembering the failure is not, since one offline blip would keep every later form in the session offering what the deployment refuses. An answer *without* the field does cache — a real answer: no restrictions. Contract pinned in `test/capabilities.test.jsx`. **`useCapabilitiesSettled()`** returns `{ capabilities, settled }` (`settled` turns true once the request is over, answer or failure), for a caller that must not decide on the `null` of "still asking" (`CreateCollectionPage`'s wrapper shows `LoadingSpinner` until it). `isOfferable(capabilities, kind, value, current)` is the predicate the forms filter their options with; `current` (the value being edited) is **always** offered even when the policy no longer allows it, mirroring the server, which only judges a *change*.
  - The module's cached `/auth/me/` fetch (`loadMe`, private) also feeds **`loadUserLanguage`** — the account's own deliberately-saved `language`, or `''` for signed-out/no-preference/failure (same fail-open shape) — which `useCollectionLanguage` reads, sharing the one request. **It checks `localStorage.getItem('userCode')` before calling `loadMe()` and asks it with `optionalAuth: true`**: `useCollectionLanguage` is reached from genuinely public pages, and without the guard an anonymous visitor on a collection with a `language` would be hard-navigated to `/login`. The `userCode` check alone misses a visitor signed in over a week ago (`userCode` never expires, the cookies do: `access_token` 1h, `refresh_token` 7d), so `optionalAuth` makes a failed request come back as a response to inspect, never a redirect, and `loadMe()` clears `userCode` itself on a definitive 401 (never on a non-401 failure), so the next protected page's `RequireAuth` still catches a dead session instead of repeating the failed refresh (a real cost against `/auth/refresh/`'s 10/minute-per-IP limit). **`loadCapabilities` asks strictly, `loadUserLanguage` optionally**: the pages that consume capabilities sit behind `RequireAuth`, and on `CreateCollectionPage` it is the only authenticated call before submit — an optional one would render the form for a >7-day-stale session and lose what was typed at the POST. A strict caller shares a strict or a successful request, and after an optional one's failure asks again strictly, which is what lets `apiFetch` redirect. Pinned in `test/capabilities.test.jsx` ("a dead session: who redirects and who does not"). **`invalidateMe()`** drops the shared cache: `EditProfilePage`'s save calls it, since that page changes `language` but neither reads nor updates this cache.
- **`useJoin`** (`src/hooks/useJoin.js`) — The shared `/auth/join/` submit behind the email-capture doors: `MagicLinkJoinPage` (`/share/:token`, plus any a deployment adds) and `JoinToAct` (inside `JoinPage`). They stay separate components because they render very differently (boxed page vs unboxed hero body with inline errors), but the request is one. Owns `email` / `loading` / `status` / `message`, the CSRF header, the 429 branch and a **ref-based** re-entry guard (a `loading`-state guard is useless against a second submit in the same tick, which runs the previous render's closure). **Never sends a `language` field**: the backend would stamp it permanently on a new user and it would outrank the joined collection's own language for every future email, with no way back short of a profile edit; the backend resolves the first magic link from the collection instead. Options: `sentMessageKey` / `errorMessageKey` and `extraBody` (`JoinToAct`'s `collection_code` plus an optional `thing_code` from `?thing=`, `SharePage`'s `share_token`). Returns `{ email, setEmail, loading, status, message, submit }`.
- **`useCollectionLanguage`** (`src/hooks/useCollectionLanguage.js`) — Applies a collection's own `language` to a page's **generic UI chrome** (`joinToAct.heading` and every other plain i18n string on the page). Takes the raw `language`/`collection_language` string from a `Collection`/`Thing`/`SharePreviewView` response (`''`/`null`/unsupported = no-op) and returns nothing. **Owner content moves too** (owner text resolves by the reader's current language, `useLocalized`), so **the owner's own translations veto it**: each page passes the raw owner texts it shows as `ownerTexts` (a headline, a description), and when one is a `{lang: text}` map holding the reader's language, nothing is overridden. What the hook does is text written once, in the collection's language, framed by chrome in the browser's. The edit pages pass the texts **as loaded/saved**, never the live draft, so typing cannot flip the form's language. Hierarchy: a signed-in visitor's own saved language always wins; failing that, `collectionLanguage`; failing that, the plain browser/localStorage default, untouched. **This hook implements only the middle tier**: given a real preference exists (`loadUserLanguage`) it stays out of the way; *applying* one on a device where it isn't the cached default is `App.jsx`'s own `/auth/me/` warm-up effect, once per visit ahead of any page. **The rule that makes its override safe**: it never writes into the `i18nextLng` cache `i18next-browser-languagedetector` reads back on the next boot (that would stamp a fresh visitor's first collection as their permanent default everywhere else — the frontend twin of the `JoinView` bug). Every `changeLanguage()` it makes (applying on mount, reverting on unmount/prop change) is followed **synchronously** by restoring the cache entry to what it found, not chained onto the returned promise: i18next's cache write happens synchronously inside `changeLanguage`, and for `es`/`ca` the promise waits on a lazy chunk, so restoring in `.then()` left the wrong value cached for the whole download. Wired into `CollectionPage`, `JoinPage`, `AddThingPage`, `DeleteCollectionPage`, `ManageInvitesPage`, `SharePage`, `ThingPage`, `RequestThingPage`, `EditThingPage`, `DeleteThingPage` (the thing pages via `ThingSerializer.collection_language`) and `EditCollectionPage` (via a dedicated `savedLanguage` state — **not** the live-edited `language` draft, which defaults to the browser language the instant the field is blank and would flip the settings form's language as the owner tries options). Tests in `useCollectionLanguage.test.jsx`.
  - **A page's data load must not depend on `t` or `i18n`**: this hook changes the language when the page's *first response* lands, which gives `t` a new identity, and a load effect listing it would run again — a second GET of the whole collection (or thing, and its transfers) and, on the edit pages, a second write of every form field from the server's copy over whatever had been typed. So the load effects of `CollectionPage`, `ThingPage`, `EditThingPage`, `EditCollectionPage` and `ManageInvitesPage` **store the i18n key** of a failure (`setError('collectionPage.noPermission')`, or `{ type: 'error', messageKey }` for a toast — `Toast` translates a `messageKey` where it paints) and the page paints `t(error)`, so the error also follows a later language change. `EditCollectionPage` reads `i18n.resolvedLanguage || i18n.language` inside the load for the draft language's *default* — a starting value, read once, behind an `eslint-disable` that says so (the precedent is `EditProfilePage`). Pinned by `test/pageLoadsOnceOnLanguageSwitch.test.jsx`: the real hook and the real `../i18n` against a collection that says `es` from an English browser, one row per page. **Known trade-off, deliberately not fixed**: each page decides its override independently from its own fetch, so navigating between two pages of a foreign-language collection shows a brief flash of the browser default in between (the outgoing page's revert is synchronous, the incoming page cannot re-apply until its response lands); closing it needs a cross-navigation, collection-keyed override state above any one page, out of proportion for the problem.

### What this deployment adds (`src/deployment/`)

The frontend half of the backend's `DEPLOYMENT_URLCONFS` / `CREATOR_POLICY` extension points. **Upstream exports nothing but empties** — the app renders exactly as if the indirection did not exist. A deployment with pages of its own **replaces the whole directory** instead of editing `App.jsx`, `LoginPage.jsx`, `SiteFooter.jsx` or the locale files (files upstream keeps changing, so editing them buys a merge conflict on every update; a directory it owns outright has none — the same trick that already works for `src/legal/{lang}.js`).

| Export | Consumed by | Meaning |
|---|---|---|
| `deploymentRoutes` | `App.jsx` | `[{path, Component}]`, `Component` usually `lazy(() => import(...))`. Mounted **above** `path="*"` — a route declared after the catch-all renders the 404 page instead, and nothing else about the app looks wrong |
| `popInPath` | `LoginPage` | Where the "new here?" button goes, or `null` for **no button at all** — the honest answer upstream, where the only ways in are an invitation and a share link |
| `aboutPath` | `SiteFooter`, `HomePage` | A page saying what this deployment *is*, or `null` for none (what OIUEEI is belongs in the README; an operator's pitch belongs to the operator). It decides the footer's about link and the dashboard empty state's second button |
| `faqPath` | `LoginPage` | Where this deployment's help/FAQ page lives, or `null` for none. Linked from `/login`, the door with the most traffic, at the foot of the page as a full-width secondary button (the shape of "New here?"); a FAQ answers questions about a *particular* deployment (who operates it, what it lets people create, how to ask for what it holds back), so it has no home upstream |
| `curatorGuidePath` | `CollectionMenu`, `InboxNotifications` | A guide for whoever runs a group, or `null` for none (upstream: what running a group means in practice is for the deployment to say). When set, it is worded "If you run a group" (`curatorGuide.link`) in two places: an entry in a **curator's** collection menu, after the downloads, and a link at the end of the `PROMOTED_CO_OWNER` notice ("you help run this group now"). ## Internationalisation (i18n)

All UI strings are externalised via `react-i18next`. No hardcoded strings in components.

- **Setup:** `src/i18n/index.js` initialises i18next with `i18next-browser-languagedetector` (detection order `localStorage` → `navigator`, the chosen language cached in `localStorage`), falling back per `fallbackLng` for unsupported languages. **English (the fallback) is bundled eagerly** in `resources` so the first paint is always translated; Spanish and Catalan load on demand through a tiny custom i18next backend (`partialBundledLanguages: true`, `load: 'currentOnly'`) — see Locale files.
- **Supported languages:** English (`en`), Spanish (`es`), Catalan (`ca`). Basque and Galician were retired (paused, not deleted — the JSONs are in git history): `fallbackLng` is an object mapping `eu` and `gl` to `['es']`, with `default: ['en']` for any other unsupported browser language, Portuguese included.
- **Locale files:** `src/i18n/locales/{lang}.json` — one JSON file per language with keys organised by namespace (common, titles, login, verify, home, collectionPage, thingPage, types, availability, condition, kinds, requestErrors…). Only `en.json` ships in the main bundle; `es.json`/`ca.json` (~55 kB each, ~18 kB gzipped) are **code-split into their own Vite chunks** via the backend's `import()` of the locale JSON and fetched only when that language is active (a non-English visitor briefly sees English before the chunk lands — `react: { useSuspense: false }`, so no spinner). `test/i18nParity.test.js` holds the three in lockstep (same keys, same placeholders, every `titles.*` ending in `— OIUEEI`) and **fails on a key nothing reads** (delete a key from all three locales when its last reader goes).
- **`html[lang]`:** updated in `App.jsx` via `i18n.on('languageChanged', ...)`, which runs after React mounts, so the first paint (and every crawler) would see the static `lang="en"` of `index.html`. `public/detect-lang.js` closes that gap: a synchronous, dependency-free script loaded via `<script src="/detect-lang.js">` (an **external** file — CSP's `script-src 'self'` has no `'unsafe-inline'` in production, `core/middleware.py`, so an inline block would be silently dropped) that mirrors `i18next-browser-languagedetector`'s priority (saved `i18nextLng` in `localStorage`, then `navigator.languages`) and `src/i18n/index.js`'s `fallbackLng` map (`eu` and `gl` to `es`; Portuguese and the rest to `en`), so it never disagrees with what i18next settles on — `detectLang.test.js` also asks i18next itself, for each code, and compares. Tested by sandbox-evaluating the real file's source (`src/test/detectLang.test.js`).
- **Usage:** every page and component imports `useTranslation` and calls `t('namespace.key')`. Select options are built inline: `AVAILABILITY_VALUES.map(v => ({ label: t('availability.' + v), value: v }))`. Plurals use i18next's `_one` / `_other` keys with `count` (`userPage.thingsCount`, `requestErrors.*_one/_other`). `import './i18n'` in `App.jsx`, before the HDS imports.
- **Nouns**, for any new copy:
  - **What a collection holds is a "cosa / cosa / thing"**, never "artículo / article". No "espacio / espai / space", "local" or "sala" for what a shed offers either — it can be machinery, a resource or an expert's time: leave the noun out where the sentence allows ("¿Cómo se reserva?"), and say "cosa" where one is needed.
  - **A group is the people; a collection is its things** — "grupo / grup / group" and "colección / col·lecció / collection" name the two halves of one object, never the same half. You **join, leave, run, are a member of, are removed from** a group, and its **members** are the group's ("Members of this group", "ask whoever runs the group"); you **create, edit, pause, delete, add things to and browse** a collection ("Create collection", "This collection is inactive"). Home's "My collections" / "Shared with me" list what you made and what is shared with you; the profile's "My groups" lists where you belong. A headline interpolated as a name (`{{collection_headline}}`) is neither and needs no noun. The emails follow the same rule.
  - **The three kinds**: a stall (es "rastrillo", ca "paradeta"), a library of things (es "biblioteca de las cosas", ca "biblioteca de les coses") and a shed (es/ca "taller") — `kinds.<K>.short` / `long` / `what` / `withArticle` / `create`.
  - **es/ca: "solicitud / sol·licitud" is a pending request** (a hold on a gift, sale, loan or rental, which the owner confirms or declines) and **"reserva" is only RESERVE_THING**, which confirms on the spot. The generic verb for acting on a card is "pedir / demanar"; where a sentence covers both it names both ("solicitudes y reservas"). **en: a pending ask is a "request", never a "hold"** ("Confirm request", "Request declined", "New request"); "reservation" stays only RESERVE_THING. Key names that say `hold` (`thingCard.confirmHold`, `thingPage.holdConfirmed`, the email's `hold_confirm_cta` / `hold_cancel_cta`) keep their names. English "Proprietary" and "Lend" stay as they are.
  - **The door for someone with no account says "Join", not "Sign in"** (`joinToAct.body` — generic until the collection has loaded — and `joinToAct.bodyActions`: the verbs are the collection's own, `utils/joinActions.js`: the thing types it allows in the cards' order, plus "add your own things" only in a COMMUNITY one, joined by the language's conjunction; "ask" is not promised): `JoinPage`'s title is "Join to take part", and the person there typed an address to *create* the account, so "Sign in" would promise something they don't have. `login.pitch` in es says "pedirlas", the generic verb.
  - **A Proprietary group is not "only you"**: with co-curators, `createCollection.modeProprietaryDesc` says "Only the team running the group adds things — you, to start with." — true even where a deployment turns co-curators off (`co_owners_enabled`).

## Testing

Smoke tests and automated accessibility checks using vitest + testing-library + jest-axe.

- **Run tests:** `npm test` (single run) or `npm run test:watch`. **Config:** `vite.config.js` — a `test` block with the jsdom environment and `src/test/setup.js` as setup file, which imports `@testing-library/jest-dom`, initialises the i18n mock and provides `localStorage`, `CSS.supports` and `ResizeObserver` polyfills for jsdom. `src/test/i18n-mock.js` initialises i18next with the real `en.json`.
- **Smoke tests:** `src/test/smoke.test.jsx` renders every page component with mocked API responses and runs `jest-axe` to detect WCAG violations (all 32 page components).
- **No state update outside `act(...)`:** `src/test/setup.js` collects React's "not wrapped in act" warnings and fails the test that produced one — and **cleans up the DOM first** (a hook that throws stops the ones after it, Testing Library's own cleanup included, so the failed test's DOM would otherwise break the tests that follow with causes that are not theirs). A test waits for the final state (`findBy…`) or uses the helpers of `src/test/settle.js`: `settle(...mocks)` lets the requests a render started finish inside `act` — it waits for every reply the mocks have handed out, a slow one included, then yields to the event loop, round after round until the calls stop growing; `press(element)` is a click whose answer lands inside `act`; `switchLanguage(i18n, lng)` changes the language inside `act`. A request held on purpose (a promise the test resolves at the end) is released and then settled, not abandoned. A page that asks something on mounting (the deployment's capabilities, for the mode notice) must be settled before a test that ends right after the form appears. **Vitest hides console output when an AI agent runs it**: to see the warnings run `npx vitest run --reporter=default --silent=false`.
- **Slow form-page tests: `dropHdsStyles()` (`src/test/dropHdsStyles.js`).** `hds-react` injects ~75 `<style>` sheets (~350 kB, ~1,700 rules) into `<head>` *when it is imported* (`css: false` does not reach them), and jsdom's `getComputedStyle` walks every rule for every element it is asked about, which `getByRole(…, { name })` does for each candidate to compute an accessible name: on `EditCollectionPage` a name query right after a DOM change cost 450–650 ms (40 ms without the sheets), and that — not typing or mounting — was 90 % of the file's time and what brushed the 20 s `testTimeout` under coverage on a loaded machine. `beforeEach(dropHdsStyles)` in `EditCollectionPage.test.jsx` and `collectionForm.test.jsx` took them from 24 s → 4.5 s and 17 s → 3.4 s with every behaviour intact (a folding `Accordion` still reads `not.toBeVisible()`: it hides with `hidden`/inline `display`, not a class rule). **Use it only where a test asserts behaviour**, not one whose point is what a stylesheet does; it is a decision per file, not a global switch. `testTimeout` was not raised.
- **Shared fixtures, pinned on both sides of the wire** (`CLAUDE.md` at the root lists all five): `src/test/hourlyGridParity.json` — cases (opening blocks, the minimum-minute step, bookings, the clock) with the start times each should produce; `src/utils/hourlyGridParity.test.js` runs `freeStartTimes` / `isHourlyPickupDisabled` over it and `core/tests/unit/test_hourly_grid_parity.py` puts every start of a five-minute sweep to `Collection.reservation_hour_violation` + `has_overlap`, so the page cannot offer a start the server refuses (or grey out a day with room) with both suites green. Add a case to the JSON rather than to either test, and keep its `note` (where the expected starts are derived by hand, so neither side copies the other's output). The one deliberate divergence: the server still accepts a full-day span across a gap, which the picker no longer offers, so no case uses one. `kindVerbParity.json` does the same for the verbs of each kind and the verb a price makes (`constants/things.test.js` ↔ `test_kind_verb_parity.py`), `nextPathParity.json` for `safeNextPath`, `inboxGroupParity.json` for the inbox's folded notices and `markdownLinkParity.json` for `[text](url)`.
- **Linting:** `eslint.config.js` runs `jsx-a11y.flatConfigs.strict`, not `recommended`: a stricter floor than the framework default, checked automatically. Its only two findings, both `no-static-element-interactions`, were the same deliberate idiom: `InfoPopover` and `TooltipButton` wrap a real, keyboard-accessible HDS `Button`/`<button>` in a plain `<span>`/`<div>` that only listens for the child's focus/blur bubbling up, to control a hover/focus-revealed panel. The wrapper is never itself a keyboard target, so the rule's fix would solve a problem that isn't there; both carry a scoped `eslint-disable-next-line` with the reasoning inline.

### The dependency audit gate (`scripts/audit-gate.mjs`)

CI runs `node scripts/audit-gate.mjs` instead of `npm audit --audit-level=high`: the same threshold (any high or critical advisory fails), but it can accept a named one, which plain `npm audit` cannot — without that a single unfixable finding leaves a permanently red pipeline or a gate dropped to `critical` that silently stops guarding every other high.

An allowlist entry requires **both** conditions, written into the script next to the id: the advisory has **no published fix**, and its vulnerable path **cannot be reached from this app**; it also records what would let it be deleted. A high with a fix we simply haven't applied must never be listed. The script flags an entry that no longer matches anything (fixed or withdrawn upstream) as a message, not a failure, so a greener audit never turns the build red.

The decision is a pure function (`evaluateAudit(report, allowlist)`), with running npm, printing and exiting around it, and importing the module runs nothing, so `scripts/audit-gate.test.js` can exercise the gate itself (a gate nobody tests can quietly stop guarding, and it looks exactly like a green build). It pins what blocks (unlisted high/critical), what doesn't (moderate/low, listed entries), that listing one advisory never stops the others blocking, that a stale entry is reported but never fails, that `npm audit`'s non-zero exit on findings is normal while a scanner that **couldn't run** is fatal, and that every real allowlist entry carries all three justifications.

**Currently allowed: nothing** — `ALLOWED` is `{}`, the state to keep it in. When the list is empty, `every real entry justifies itself on both counts` iterates nothing, so a companion test pins the bar itself against entries that must fail it; keep that pairing if you ever add an entry back.

### HDS Select quirks

Every `<Select>` must say which language HDS should speak, because its own assistive wording ("choose one", "2 selected options", "clear current selection") defaults to **Finnish**. **In HDS 6 it lives inside `texts`** — `texts={{ label: …, language: 'en' }}`; the HDS 5 `language="en"` prop is ignored silently (the component renders, the page looks right, and only what a screen reader reads out changes; no axe rule compares the language of an `aria-label` with the page's). `src/test/selectLanguage.test.jsx` renders one such form *and* sweeps the source for the dead prop, since the failure is invisible on screen. `'en'` is the honest value everywhere: HDS ships fi/sv/en and none of this product's three locales is among the other two.

`DateInput` and `Accordion` do honour a `language` prop (verified), and every call site passes `hdsLang(i18n.language)` (`'en'` for es/ca/en). `DateInput`'s `language` only reaches fi/sv/en, so its calendar's **month and weekday names stay English** for an es/ca reader (HDS bundles only those three date-fns locales, hard-keyed off the prop; there is no seam for a fourth). What *is* reachable are three label props, which `RequestThingPage`'s four `DateInput`s pass from i18n (`datePicker.open` / `.select` / `.close` → `openButtonAriaLabel` / `selectButtonLabel` / `closeButtonLabel`); `dateOutsideRangeErrorText` / `malformedDateErrorText` are localised too. Full es/ca months and weekdays would mean replacing the calendar itself — deferred, and if done it goes in both editions, not deployment-only. `RequestThingPage.test.jsx` pins the wiring.

**The help line is `texts.assistive`, not `helper=`**: the HDS 6 `Select` has no `helper` prop (it is ignored silently, the sentence never reaches the page — four selects lost theirs that way). `assistive` prints the line under the field and says it to a screen reader **inside the control's own `aria-label`** ("Language. 1 selected option: … <the line>"); it sets no `aria-describedby`, so a test reads `toHaveAccessibleName(expect.stringContaining(line))`, not `toHaveAccessibleDescription`.

Other API notes: `value` is an array of the selected **option objects** (`[{ label, value }]`), `onChange` receives an array (`(sel) => sel[0].value`), error text uses the `error` prop (a string), not `errorText`. The `icon` prop renders inside the one `<button role="combobox">`, before the placeholder text. **Handed a bare string it cannot resolve against `options`, the combobox renders that string verbatim** (a raw `GIFT_THING` once showed in `ThingForm`'s type box): always pass `options.filter(o => o.value === current)`, never the raw value.

The quirks in this section were last checked against `hds-react@6.0.8`.

### HDS ToggleButton quirks (v5)

1. **`onChange` receives the current value, not the new one.** Always negate: `onChange={(val) => setState(!val)}`.
2. **`style` targets the inner `<button>`, not the flex container**, so flex-layout overrides via `style` have no effect.
3. **HDS has no helper text for it**, so the label carries the title and the explanation together, in one line of text that wraps by itself (`variant="inline"` as HDS draws it: text on the left, the pill on the right). The whole sentence is one locale key per label ("Title: explanation.", or "Title (explanation)" when the explanation holds a colon), so each language decides its punctuation; never concatenated in JSX. The button's accessible name (`aria-labelledby` the label) is that sentence.
4. **`disabled + checked` renders light grey**, and that is how the one always-on toggle (`#notify-magic`) is left: `App.css` has no rule for it, and `alwaysOnToggle.test.js` keeps it so.

### Links — three kinds, and why HDS `Link` is not used for the third

> **A link that looks like a button** (below) is a fourth kind: a router `Link` around an HDS `Button` is now `ButtonLink`, built on HDS's own `Link`. So the app does import HDS `Link`, just not for kind 3, where the reasoning below stands.

Under DESIGN §1 a component HDS ships and the app skips needs a reason. "Link" here means three different things:

1. **Internal navigation** — react-router's `Link`, and it has to be: an HDS `<a>` would reload the SPA. The overwhelming majority, and not a deviation at all (HDS has no router).
2. **Generated HTML** — `MarkdownText` builds `<a href=…>` as a **string** and injects it; a React component cannot go there without rewriting the renderer, and that renderer is where the escaping invariant lives. Off the table.
3. **External links in JSX** — five sites (`ApprovalNotice`, `PdfUpload`, `LoginPage` ×2, `EditProfilePage`), all `<a target="_blank" rel="noopener noreferrer">` (`FeedbackLink` became an HDS `Link` button and found that `openInNewTab` prints its label). **This is the one HDS `Link` should own**: `external` + `openInNewTab` render the outbound icon and announce the new tab, which none of the five do today. What keeps it from happening is that it is a **copy change in three languages**: HDS's `openInNewTabLabel` defaults to Finnish (the same trap as `Select`'s language), so adopting it means new i18n keys ×3 plus a visible label and icon appearing next to five links — including two inside `<Trans>` placeholders. A design decision with visible consequences, not a refactor.

### HDS SelectionGroup quirks

Three, and the first fails **silently** (learned replacing the hand-rolled `<fieldset>` in `CollectionModeField`):

1. **It does not flatten its children.** `{options.map(...)}` arrives as a single child that *is* an array, `isValidElement` rejects it, and the group renders empty — a fieldset with a legend and no radios, no error anywhere. Pass one flat array: `{[...optionFields, <Extra key="…" />]}`.
2. **It re-wraps every child in a `<div key={child.props.id}>`.** A child without an `id` prop gets `key: undefined` and React logs a missing-key error for each; children that are wrappers rather than HDS controls therefore carry an `id` they have no other use for.
3. **That wrapper `id` must NOT be the same string as the `RadioButton`'s own `id`.** Give it a distinct one (`CollectionModeField` and `RadioOptionGroup` use `${id}-option`): two elements in the DOM sharing one `id` make `<label for="…">` resolve to the first it finds (the empty wrapper), so **every radio's accessible name goes blank** — which passes a bare radio-count assertion (`getAllByRole('radio')`) and fails only a name-scoped query (`getByRole('radio', { name: … })`).

It also owns the vertical rhythm (`--spacing-row`, a grid `gap`), so per-option margins are its job, not the caller's.

### HDS accessibility bugs we carry

Found by keyboard testing in `hds-react` (first found in 6.0.5; neither the 6.0.6, 6.0.7 nor 6.0.8 release notes fix any of them), all verified against the shipped bundle rather than the docs. The decision each time is deliberate: **stay on HDS, work around it only where the workaround is itself an HDS API, and wait for upstream on the rest.** Delete an entry here when a release fixes it — do not let one rot into a permanent local fork.

**1. `Linkbox` announces as a region, not a link.** It renders `<div role="region" tabindex="0">` with the real `<a>` inside at `tabindex="-1"` and activates it from an `onKeyPress` handler (a deprecated React alias). So the card *is* reachable (one tab stop) and Enter *does* follow it, but it is announced as "region", it never appears in a screen reader's list of links and **Space does not activate it**. HDS's own documentation site renders identical markup, so this is theirs. **Not worked around** — the only fix is to stop using the component, which costs more than the defect. Affects `CollectionLinkbox` (the grids on `HomePage` and `UserPage`). **One more thing the same design does, which we do work around**: the region's own `onClick` answers any click inside it with `link.click()` — a fresh click with no modifier keys — so a ctrl/cmd/shift/alt click on a row would open the new tab *and* move the current one. `CollectionLinkbox` leaves such a click to the browser and stops it reaching the region (`stopPropagation`); a plain left click routes in-app. Pinned in `CollectionLinkbox.test.jsx`.

**2. A deletable `Tag` has no name for what it does.** v6 makes the *whole chip* the control — one `<div role="button">` named from its own text — and has no `deleteButtonAriaLabel` prop: a screen reader announces "button, Vintage" and nothing about removal. **Worked around**: `TagInput` passes its own `aria-label` (the rest props land on that div, last in the `Object.assign`, so it wins). Pinned by `TagInput.test.jsx`.

**3. Nine components hard-code their focus ring to `var(--color-coat-of-arms)`** instead of reading `--color-focus-outline` as the rest of HDS does — `DatePicker` days, `DialogHeader`'s close and title, `Linkbox`, `Notification`'s label, `Table`'s sort button, `ToggleButton`. They also set `outline: none` and draw their own `box-shadow`, at a specificity a global rule cannot reach, so the two-tone ring in `App.css` does not apply to them (see the focus-ring comment there for why a single colour fails: `#0072c6` clears 3:1 on only 31 of the 48 theeeme surfaces).

**4. Icons carry no `aria-hidden`.** `IconFoo` renders a bare decorative `<svg>`, so **every** call site adds `aria-hidden="true"` itself (or a label, when the icon is the only content). There is no default and no lint rule.

**5. An inline `Notification` is announced by nobody.** It gets `role="alert"` **only** when it is positioned (a toast); inline it gets no role at all, so a failed Save is silent to a screen reader (WCAG 4.1.3 Status Messages, AA). The role cannot be supplied from outside either: HDS spreads rest props *before* its own `role: … : void 0`. **Worked around** by shape: a message that is *appended* to the page goes inside `StatusRegion`, a live region that renders unconditionally so it pre-dates its content; a message that *replaces* the form gets HDS's `autofocus`, which both rescues the focus the vanished submit button held and gets the message read. A load error that *is* the page needs neither (it is read in document order). A test therefore cannot look for `role="alert"` on one.

**6. `Link`'s new-tab and external-domain labels default to Finnish** (`"avautuu uudessa välilehdessä"`, `"Siirtyy toiseen sivustoon."`) — the same trap as `Select`'s `language`, and as invisible (it only changes what is announced). Any adoption of `Link` with `openInNewTab` or `external` **must** pass `openInNewTabLabel` / `openInExternalDomainAriaLabel` in all three locales.

**7. A `SelectionGroup`'s `errorText` is linked to nothing.** It renders a plain `<div>` after the options — no `id`, no `aria-describedby` from the fieldset or its inputs, no live region — so it is visible but never announced (verified in the `hds-react@6.0.5` bundle). **Worked around** where it matters: `RequestThingPage` moves focus to the first option of the group it flags on a failed Reserve, so the question is read out; the text stays HDS's.

### A link that looks like a button: `ButtonLink`

`Button` always renders `<button>` — there is no `as` or `href` prop — and wrapping it in a router `<Link>` produces nested interactive elements: **two tab stops for one control**, announced "link… button", with the `<a>` taking the focus ring while the `<button>` carries the look. `jsx-a11y` has no rule for it and **axe reports no violation**, which is how they accumulated. HDS's own answer is `Link`'s `useButtonStyles`, which swaps the link class for `hds-button hds-button--primary` — the real button CSS, the same `--computed-*` token chain. `src/components/ButtonLink.jsx` wraps it:

```jsx
<ButtonLink to={editPath} fullWidth style={btnSecondaryStyle}>{t('common.edit')}</ButtonLink>
```

Load-bearing:

- **There is no `variant` prop.** What makes a button secondary here is the token set (`btnSecondaryStyle`), not HDS's variant class (`hds-button--secondary` is a hashed CSS-module name we could not address), so the same element serves both.
- **`fullWidth` is ours** (`.button-link--full`, one declaration): `Link` has no such prop, and the base class already centres the label.
- **The `<a>` it renders IS the button**: `hds-button--primary`'s background, border and padding sit on the `<a>` itself, with a `<span>` inside for the label. So a rule that removes the `<a>`'s box (`display: contents`, `display: none`) paints none of that and drops it out of the a11y tree (an old `.thing-card-buttons a { display: contents }` once stripped the card's primary "Edit" to a bare text link; removed, with a source-sweep guard in `ButtonLink.test.jsx`).
- **Only a plain left click is intercepted.** A cmd/ctrl/shift/alt or middle click falls through to the real `href`, so open-in-new-tab keeps working — the thing hand-rolling this usually loses. Pinned by five cases in `ButtonLink.test.jsx`.

This flips the element's role: a test looking for `getByRole('button')` on one of these has to look for `link`. And **a regex will undercount them** (a sweep missed `<Link>`s that held a ternary rather than a `<Button>` directly); the runtime invariant (`nestedInteractive.js`) is the one that finds them, grep did not.

## OIUEEI Customization Layer

The project consumes HDS directly from npm and applies three local overrides:

- **Fonts** (`src/fonts/oiueei-fonts.css`) — the **Curiosa** variable font (`public/fonts/curiosa/Curiosa-Variable.woff2`, weight + italic axes), declared via `@font-face` as `font-family: "Curiosa"` and served by Vite at `/fonts/curiosa/`. The HDS `--font-default` token's *value* is overridden to `"Curiosa", Arial, sans-serif` in `src/styles/oiueei-theme.css` (the token *name* is kept, so every HDS component resolves it). The font binary is gitignored (licence); a clone without it falls back to Arial / system sans.
- **Colors** (`src/styles/oiueei-theme.css`) — CSS custom property overrides imported after `hds-design-tokens` to take precedence: the font, the focus-outline decisions and the fallback values of the app's own palette (`--color-braaanding-01` … `06`, see above).
- **Logos & brand assets** (`src/assets/`) — OIUEEI logos, placeholders and favicon.

## Key Configuration (`vite.config.js`)

- **React deduplication** — aliases `react` and `react-dom` to the frontend's `node_modules` to prevent dual-copy hook errors (some HDS internal deps declare a React 17 peer).
- **Proxy** — `/api` forwarded to `http://localhost:8000`; dev server on port 3000.
- **A file of `public/` cited from JS goes through `import.meta.env.BASE_URL`** (`` href={`${import.meta.env.BASE_URL}cocina-ejemplo.zip`} ``). Production builds with `base: '/static/'` and Vite rewrites the paths it can see in `index.html` and CSS `url()`, but **not a literal inside JS**: `"/cocina-ejemplo.zip"` fell through to the SPA catch-all and downloaded `index.html` under a `.zip` name, while in development, where the base is `/`, both spellings are the same URL. A component test cannot tell them apart (`BASE_URL` is `/` under vitest), so `test/publicFileLiterals.test.js` sweeps the source: no non-test `.js`/`.jsx` under `src` may hold a literal that opens with `/` + a name found in `public/` (the directory is read, not listed).
- **Code splitting** — every page is `React.lazy`-loaded in `App.jsx` (the `Routes` block is wrapped in a `Suspense` whose fallback is `LoadingSpinner`), so each route ships as its own chunk and page-only deps (papaparse, qrcode, jszip) load on demand. `build.rollupOptions.output.manualChunks` splits `vendor-react` and `vendor-hds` from app code for long-term caching; `chunkSizeWarningLimit` is **650 kB** because the shared `hds-react` chunk is **~633 kB raw / ~164 kB gzipped** (measured on 6.0.8; it grows a few kB each time a new HDS component is adopted). Tree-shaking works — `CookieConsent`, `Hero`, `Footer`, `Pagination`, `Stepper`, `Tabs` and `Breadcrumb` are absent from the built chunk — so the size is what we genuinely use.
- **A tab open across a deploy reloads once instead of dying** (`src/utils/reloadOnStaleChunk.js`, installed in `main.jsx` before the first render). A release ships only the *new* hashed chunks, so a tab opened before it asks, on its first visit to a page it had not loaded, for a chunk that is gone; `lazy()` rethrows and the top-level `ErrorBoundary` would replace the app with "Something went wrong". Vite dispatches a cancelable `vite:preloadError` on `window` when a dynamic import fails; the listener records the time in `sessionStorage` under `staleChunkReloadAt`, calls `preventDefault()` and `location.reload()`, which fetches the current `index.html` and with it the current chunk names. **The reload only helps if `index.html` is fetched afresh**, so `spa_index` (`config/urls.py`) serves it with `Cache-Control: no-cache` (`test_spa_index.py`). **One reload per 10 s, never a loop**: a second failure inside the window is *not* prevented and reaches the `ErrorBoundary`, so a really gone chunk (a broken release) cannot spin the page. And **when the mark cannot be read or written the page is not reloaded** — blocked storage, quota, private mode, even a `SecurityError` on merely touching `sessionStorage` (all in try/catch, the lookup lazy so installing can never stop the app rendering) — because reloading without being able to remember it is the loop being avoided. This is the app's only `sessionStorage` key, so README §Privacy's inventory names it and `test/browserStorage.test.jsx` pins both (one module may mention `sessionStorage`, its key is the one the README lists); the README half runs only in the standalone (a deployment keeps every source file but replaces `README.md` and publishes its own storage inventory, so it guards that itself). Unsaved input on a page that had *not yet* failed is not at risk (only unloaded chunks fail). Tested in `reloadOnStaleChunk.test.js`, not in a browser.

- **A tab left open across a deploy says so** (`src/hooks/useNewVersion.js`, shown by `components/NewVersionNotice.jsx`, mounted once in `App.jsx`). The reload above only fires when a chunk is missing; a tab that never opens a new page keeps its old texts and code for as long as it lives. In production only (`import.meta.env.PROD`), when the tab comes back into view (`visibilitychange` to `visible`) and at most once every 10 minutes (`CHECK_EVERY_MS`, counted from the last attempt, a failed one included), the hook `fetch('/')` — same origin, no parameters, no headers of its own, so it is no tracking: the server already serves `index.html` with `Cache-Control: no-cache` (`spa_index`) — reads the entry `<script type="module" src>` out of the answer (`DOMParser`, nothing executes) and compares its address with the page's own. Every build names that file after its content, so a different name is a newer build. If it differs, `NewVersionNotice` shows a small HDS `Notification` (`info`, `bottom-right` so it never covers a toast, which stands at the top) that does not close by itself: `newVersion.body` and a themed **"Reload"** button (`location.reload()`) beside the notification's own close. **Nothing reloads on its own** — a form may be half written — and a request that fails, an error status or a page with no entry script says nothing and tries again at the next window. Once it has shown, the hook stops asking. Nothing is stored in the browser (the time of the last check is a variable), so `/legal` and README § Privacy need no new key. Pinned in `hooks/useNewVersion.test.jsx` (same script → nothing, different → the notice with Reload and close, the request is `fetch('/')` and nothing more, two returns inside ten minutes → one request, hidden tab → none, failure → nothing and the next window retries, development → none, Reload calls `location.reload`, closing hides it for good); not seen across a real deploy.

## Authentication Flow

1. The user enters their email on `/login`.
2. The backend sends a magic link pointing to `localhost:3000/verify/{rsvp.token}` — the high-entropy token, never the 6-char RSVP code.
3. `/verify/:code` calls the backend, which sets JWT tokens as HttpOnly cookies on the response.
4. `userCode` is stored in `localStorage` (for ownership checks only — auth tokens are never in localStorage).
5. Authenticated pages use `credentials: 'include'` to send the cookies. On 401, `apiFetch` silently attempts a token refresh via `POST /api/v1/auth/refresh/`; if the session is gone it redirects to `/login?next=<the page>` and the magic link brings the reader back to it.
6. `userCode` determines ownership (e.g. hide the reservation button on own things).
7. The CSRF cookie is obtained on app load via a GET to `/api/v1/auth/me/` — a plain `fetch`, deliberately not `apiFetch` (a signed-out visitor's 401 must not trigger `apiFetch`'s refresh-then-redirect-to-login). The same call applies a signed-in visitor's own saved `language`, if set, via `i18n.changeLanguage` — the top tier of the hierarchy `useCollectionLanguage` otherwise only ever vetoes, never actively applies.
