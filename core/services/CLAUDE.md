# Services Documentation

Business logic and side effects extracted from views into `core/services/`. Keeps views thin and logic reusable.

## Modules

### `app_palette.py` and `palette_contrast.py` — The app's own palette in the page

`app_palette.inject_app_palette(html)` writes the `Braaanding` row (`core/models/braaanding.py`, the palette of everything that is not a collection's page and of the emails) into the `<head>` of every `index.html` `spa_index` serves: a `<style id="braaanding">html:root{--color-braaanding-01:#…;…06}</style>` and a `<meta name="braaanding-koro" content="…">`. So the first byte already has the right colours: no request, no flash. **Why `html:root`:** the stylesheet keeps the seeded values as a fallback in a plain `:root` (`frontend/src/styles/oiueei-theme.css`: the Vite dev server does not go through Django), and one type selector more makes the served values win whatever the order of the two in the document. **Why a `<meta>` for the koro:** a script reads it synchronously and the CSP has no `'unsafe-inline'` for scripts, so an inline data block is out and an extra request would flash. The CSP already allows the inline `<style>` (`style-src 'unsafe-inline'`). **Every value is checked again at the point of writing** (a hex is exactly `#RRGGBB`, a koro is one of the six, else the seeded default): this writes into markup. It runs on every page, a collection's included (its page paints over the app's colours once loaded) and costs no query: `braaanding()` remembers the row in the process for 60 seconds (the pages that promise to ask the database nothing — the site card, the neutral routes — keep that promise in steady state; a worker's first view in a minute spends one query), and the process that saves the row forgets at once. `palette_contrast.py` is the WCAG formula and the pairings the admin refuses a palette on (see [`Braaanding`](../models/CLAUDE.md#braaanding)).

### `link_preview.py` — The `<head>` of a shared link

WhatsApp, Telegram, Signal, iMessage and Slack read the HTML the server sends and run no JavaScript, and `spa_index` serves one `index.html` for every route, so a shared link used to show only "OIUEEI" and the icon. `spa_index` reads the route without touching the database (`route_for_preview`); only when the route is a candidate does it spend the visitor's share of `ANON_API_RATE`, and then it looks the target up (`preview_for_route`) and, when that answers, serves `inject_preview(html, preview, absolute_url)`.

| Route (trailing `/` optional) | Previewed when | Filled in |
|---|---|---|
| `<prefix>/<code>` and `<prefix>/<code>/join`, for each prefix in `PREVIEW_COLLECTION_PREFIXES` (`collections`, `stall`, `library`, `shed`) | `collection.can_view(None)` | name, description, photo |
| `<prefix>/<code>/things/<thing>` (same prefixes) and `things/<thing>` | `thing.can_view(None)` | name, description, photo |
| `share/<token>` | `share_token=token` and `ACTIVE` (the filter of `SharePreviewView`) | name, description, **no photo** |

Anything else, and any of the above whose condition fails, gets `None` and is served **the site's card** (`site_preview()`: title "OIUEEI", `generic_parent_pitch` in the deployment's `EMAIL_LANGUAGE`, no photo, `og:url` the site's own root and never the page's) — **the same bytes for every such page**, so a private collection cannot be told from a code that does not exist (`/` and `/login` carry it too, which is the card of the instance's own address). It costs no query and spends no allowance, and a path that is none of the routes above costs no query at all.

- **The rule is "only what an anonymous visitor could already read".** The condition is the model's own `can_view(None)`, never a copy of it.
- **`share/` carries no photo on purpose**, like the endpoint behind the join page: the card must not give the holder of a link more than the join page does.
- **Tags**: `<title>{name} — OIUEEI</title>`, `description` and `og:description` (only with a description), `og:title`, `og:site_name`, `og:type`, `og:url` (absolute, no query string), `og:image` (only with a photo, via `asset_url`) and `twitter:card` (`summary_large_image` with a photo, `summary` without). Every value goes through `escape`: they are an owner's words inside attributes. No fallback image: without a photo the app shows its icon as before.
- **Language**: the crawler has no reader language, so name and description resolve with the collection's (a thing's: that of its first collection), falling back to `es`.
- **Description**: `plain_description` turns Markdown into one line (links keep their text; heading, list, emphasis and table marks go; whitespace collapses) cut at 200 characters on a word boundary with `…`. **A collection (or share link) with no description in the resolved language gets the sentence of its kind** (`kind_what_STALL`/`LIBRARY`/`SHED` in `email_texts`, spoken in the collection's language — the same words as `kinds.<K>.what` in the app, held equal by `test_kind_what_parity.py`), so a card is never only a title and gives no more than the join page does; a thing's card is unchanged.
- **Queries**: one for a collection (two once the address redirect has looked at its kind); three for a thing (the thing, the visibility check, its collection for the language). A page under the wrong prefix never gets here: `config.urls.collection_address` answers it with a 301 first, so the preview only sees the right one.

### `booking_service.py` — Booking Business Logic

Handles state transitions for `BookingPeriod` and `Thing` models as an atomic unit.

#### Functions

| Function | Input | Behaviour |
|----------|-------|-----------|
| `cancel_booking(booking)` | `BookingPeriod` instance | Calls `booking.cancel()`. For single-use types (GIFT, SELL), restores thing to `ACTIVE`. Clears the owner's request notification (see below). Returns thing. |
| `accept_booking(booking)` | `BookingPeriod` instance | Calls `booking.accept()`. For single-use types, sets thing to `INACTIVE` and adds requester to `deal` M2M. Creates a `ThingTransfer` record (from owner to requester, lent_date = start_date or today). Returns thing. |
| `reject_booking(booking)` | `BookingPeriod` instance | Calls `booking.reject()`. For single-use types, restores thing to `ACTIVE`. Returns thing. |
| `compute_availability(blocked_periods, today=None, horizon_days=90, allowed_weekdays=None, durations=None)` | iterable of PENDING/ACCEPTED bookings (objects with `start_date`/`end_date`), plus the governing collection's rental rules | **Pure, side-effect-free.** Returns `(available_today: bool, next_available: date|None)` for a date-based thing. Walks forward from `today` (default `timezone.localdate()`), treating each booking `[s, e]` as blocking pickup on `[s, e)` — the return day `e` is free for the next pickup (matching `BookingPeriod.has_overlap()`'s strict overlap / back-to-back handovers) — and returns the first day a pickup could start, or `(False, None)` when no day within `horizon_days` qualifies. Null-dated rows are skipped. **`allowed_weekdays` (0=Mon…6=Sun) + `durations` (days) are the rental rules (#7)**: a day counts only if its weekday is allowed, it is free for pickup, and — when the collection fixes the lengths — at least one length both lands its return day on an allowed weekday and fits without a strict overlap. This mirrors `frontend/src/utils/rental.js::isPickupDisabled` exactly, so the card and the date picker can't contradict each other (the bug: a Wednesdays-only collection with next Wednesday booked reported "available today" on a Monday). Either rule may be passed alone; with neither the walk is byte-identical to the unrestricted one. Consumed by `Thing.availability_window()` → the `available_today`/`next_available` serializer fields. **Untouched by the HOUR-unit work** — still the LEND/RENT and `DAY`-unit RESERVE walk, byte for byte. |
| `compute_hourly_availability(blocked_periods, collection, today=None)` | same booking iterable, plus the `HOUR`-unit collection itself | The `HOUR`-unit twin, not a modification of the function above — same `(available_today, next_available)` shape so `Thing.availability_window` treats both units alike. "Available" means *some* opening block that day still has a gap of at least the collection's own `reservation_min_minutes` (via the private `_day_has_a_free_hour`, which sweeps that day's bookings — a whole-day one, `start_time` NULL, closes the day outright — against `collection.day_opening_blocks()`); it does not check whether a *specific* duration/start-time combination is offered, which `RequestThingPage` works out itself once a day is picked. The gap has to hold the minimum **at a start on the step grid** (every `reservation_min_minutes` from the block's opening — the grid `reservation_hour_violation` enforces and the picker walks, 2026-09-18), not just be long enough: a 60-minute gap from 10:30 on a 60-minute grid from 10:00 is no slot at all, and counting it made the card say "available" on a day the picker greys out. **Fixed 2026-09-18**: `_day_has_a_free_hour` compared every gap against a hardcoded 60 from the day it was written, unchanged when 0150 made the minimum configurable — a collection with a sub-hour minimum (the reason 0150 exists) reported a day unavailable even with room for the shortest reservation it actually offers. Found in review, live in production one day before the fix. Walks `collection.reservation_horizon_days` ahead, same shape as the day-based walk, counting **today's** starts only from the current minute of the deployment's clock (`TIME_ZONE`; an optional `now`), so a gap that has slipped into the past doesn't report "available today" — and parsing the collection's `closed_dates` once for the whole walk and handing the set down (`_day_has_a_free_hour(..., closed=)`) rather than once per day. |

##### The team — `team.py`, and why a notice costs no query per collection

`Thing.managers()` and `can_manage()` walk every collection a thing sits in, reading each one's owner and co-curators. **`core/services/team.py`** holds the two pieces that make that free: `managers_ready_collections()` (the `Collection` queryset with `owner` selected and `co_owners` prefetched, used as `Prefetch("collections", queryset=managers_ready_collections())`) and `load_team(thing)` (applies it to one instance — **a no-op when the caller already prefetched**, a constant two queries when it did not). It lives in `services` because `booking_service` needs it and a service never imports from a view; the views import it from here. Every fan-out to the team uses it: a FAQ question, its answer and its hiding (`_faq_with_team()` in `faq.py`), a hold request (`ThingRequestView`), its decision (`BookingActionView`, `VerifyLinkView._handle_booking_action`, and `finalize_booking_decision` itself, which calls `load_team(booking.thing_code)` because `accept_booking`/`reject_booking` return a freshly **locked** `Thing` with no collections and would otherwise be the one place that pays per collection), and a reservation made or cancelled. `TestNoticeFanOutQueryBudgets` (`test_query_counts.py`) runs each of them with the thing in one PROPRIETARY collection and in three and demands the same number of queries; each prefetch has a test that goes red without it. **Not measured by "a co-curator is recognised":** `can_manage` stops at the first collection they curate, so the budget that shows a missing prefetch is the one that *refuses* someone (a full walk) — hence the outsider and demoted-co-curator cases.

**`drop_team_notices_of(user, collection)`** is the other end of that role (it takes the `INVITE_PROPOSED` of the collection too — a recommendation is put to the whole team and nobody who stopped running the group can decide it): when someone stops running a collection — demoted (`CollectionCoOwnerView.delete`) or removed from the group while a co-curator (`CollectionInviteView.delete`) — it takes out of **their** inbox the team notices (`InAppNotification.team_booking_notices`) whose `payload.collection_code` is **that** collection, because they still asked for a decision the server would now refuse. It keeps what is theirs as a person (their own requests' answers, `DEMOTED_CO_OWNER`, group messages — none is a team notice), what another group they still run sent them, and **any notice about a thing they still manage** (`can_manage`: a COMMUNITY member who contributed it, or one in another PROPRIETARY group they curate). **`FAQ_QUESTION` is handled too**: its payload carries the thing's `collection_code` since it was written with one (a question from before that has none and stays), and its thing is read from the FAQ (`faq_code`) for the "a thing they still manage" test; a manager's `RESERVATION_CANCELLED` copy carries no `collection_code` and stays. Call it after the role is removed so `can_manage` sees the new state.

The requester's own access is the other per-collection cost on these paths: `resolve_request_collection` used to ask `Collection.can_view` of each collection in turn, and for a private one that is an `is_invited` query apiece. `_readable_collections` settles membership in **one** query for the whole list and hands it to `can_view(..., invited_to=)`; the visibility rules themselves stay in `can_view`.

##### Reservation requests

These own the **create** side (formerly the `ThingRequestView._handle_*` methods). Each performs the locked create + status transition, then fans out the request emails + in-app notification + `HOLD_REQUESTED` event via the shared `send_*_request_notifications()` helpers. Rule violations raise `BookingRequestError(message, status_code, code=None, params=None)`; `ThingRequestView` catches it and returns `exc.as_body()` — `{"error": message}` plus `code`/`params` — with that status (default 400; 409 for a date overlap). A `core.utils.Refusal` from the model (`reservation_violation`, `reservation_hour_violation`, `rental_violation`) brings its own code and params, so `raise BookingRequestError(violation)` needs nothing more; every refusal is coded so the SPA can say it in the member's language (`core` has no gettext). Serializer validation stays in the view.

| Function | Input | Behaviour |
|----------|-------|-----------|
| `require_a_seat(thing, requester)` | LEND/RENT/GIFT/SELL | Asking for a thing is being part of the group that lists it: raises `BookingRequestError(403, code="not_a_member")` unless the requester is in `invites` of, or is a curator (`is_curator`) of, at least one **ACTIVE** collection of the thing. Called first by `request_date_based_booking` and `request_standard_booking`. Before it only a reservation demanded membership, so a signed-in reader of a PUBLIC group could ask without being a member — the person running the thing could not open their profile and they never received the group's summary, unlike someone who arrived without a session (the magic link joins them). Memberships are settled in one query; collections come prefetched manager-ready by the view. |
| `request_date_based_booking(thing, requester, start_date, end_date, rental_collection=None, collection_code=None)` | LEND/RENT | Enforces `rental_collection.rental_violation()` (400) and `BookingPeriod.has_overlap()` (409), then creates the dated booking. Returns the booking. |
| `request_standard_booking(thing, requester, collection_code=None)` | GIFT/SELL | Re-checks availability + duplicate under the lock; creates the booking and flips a non-endless thing to `TAKEN`. Returns the booking. |
| `resolve_rental_collection(thing, collection_code=None, requester=None)` | LEND/RENT | Picks the collection whose rental rules apply (the passed `collection_code` **when the requester may read that collection** — a code naming any other is ignored, so it can't pick the looser rules of a group the requester was never in — else the thing's first collection with rules, else `None`). |
| `resolve_request_collection(thing, collection_code=None, requester=None)` | any | Picks the collection a request was **made through**, for the notification payload **and the requester's emails' `email_note`**. The request's own context wins (`collection_code`, sent by the SPA from the card/detail page it was showing); without it — the standalone `/things/:code` page — it approximates: the rental-rules collection, else the thing's first ACTIVE one, else `None`. A thing lives in one collection now, so the guess only matters for a row from before that rule; the SPA passing the code is what makes it exact. **With a `requester`, only collections they may read (`Collection.can_view`) are candidates** — for the named one and both fallbacks: the code is the client's to send and the first collection with rules can be a PRIVATE group they aren't in, whose note then reached them by email. Both callers pass one: `send_booking_request_notifications` and `finalize_booking_decision`. |
| `send_booking_request_notifications(...)` | — | For **every manager of the thing**, minus the requester: their own RSVP accept/reject pair (`RSVP.create_booking_pair(booking, manager)`, minted to them) + their own request email with those links + an in-app `BOOKING_REQUESTED`; then the requester's confirmation and the `HOLD_REQUESTED` event (2026-09-29). The recipients' addresses are their own (`manager.email`), so no `owner_email` is threaded through the GIFT/SELL/LEND/RENT path any more; RESERVE_THING still takes it. `request_standard_booking` keeps the **caller's** prefetched `thing` for this fan-out and works on a separate `locked` row inside the transaction: the row read under `select_for_update` carries no collections, and every manager would cost a query per collection. |

##### On-site reservations (RESERVE_THING) — a different shape

Auto-confirmed: the booking is created straight to `ACCEPTED`, **no RSVP pair**, **no ThingTransfer**, both parties emailed at once. The accept/reject/`finalize_booking_decision` machinery is never reached for it.

| Function | Input | Behaviour |
|----------|-------|-----------|
| `resolve_reservations_collection(thing, collection_code=None)` | RESERVE | The reservations collection the request is made through (`collection_code` hint, else the thing's first reservations collection). `None` only for a misconfigured RESERVE thing in no reservations collection — the caller turns that into a 400. |
| `request_reservation(thing, requester, owner_email, start_date, duration_days=None, project_note="", collection_code=None, *, start_time=None, end_time=None)` | RESERVE | **Two shapes, chosen by `rc.is_hourly_reservations()`, never both**: a `DAY`-unit collection takes `duration_days` (the original shape, byte-identical to before); an `HOUR`-unit one takes `start_time`/`end_time` instead, validated by `Collection.reservation_hour_violation()` rather than `reservation_violation()`, and the stored booking still gets `end_date = start_date + 1` — never a date range — so every date-only downstream consumer (reminders, `close_transfers`, the calendar export's date filter) keeps working unchanged; only `has_overlap()` is told about the hours. Common to both: 403 unless the requester is a collection member (`code="not_a_member"` on the raised `BookingRequestError`, so a client can tell this specific 403 apart from this endpoint's other one — `get_viewable_thing`'s "not authorized", which carries no code — `RequestThingPage`'s auto-join keys off it precisely so it can't fire on the wrong 403); **`Collection.active_reservation_count()` against `reservation_max_active_per_member`** (400, a courtesy cap — not locked the way `has_overlap` is); `has_overlap()` (409, passed `start_time`/`end_time` under `HOUR` so the clash check narrows to a time-of-day comparison on a shared day). Creates the `ACCEPTED` booking, sends the requester's confirmation and — to **every manager** of the thing (`Thing.managers`, deduped), minus the requester if they are one — the notice email + `RESERVATION_MADE` in-app. **A request that overlaps the thing's pause is refused first** (`Thing.pause_overlaps`, read from the row locked here; 409 `thing_paused`), in `request_reservation` and in `request_date_based_booking` alike. **With `Thing.units` > 1**, under the same Thing lock: first the one-person-at-a-time rule (`has_overlap(..., requester_code=requester)` on that person's own bookings: a 409 coded `reservation_one_per_person`), then `has_overlap(units=units)`, which is `saturated_periods`, the rule the browser is served. With one unit neither changes anything. Logs `HOLD_REQUESTED` **and** `HOLD_ACCEPTED` (the funnel is instant). The optional `contact_phone` is stored only when the collection asks (`reservation_asks_phone`) and is never passed to any email or to the calendar export. |
| `cancel_reservation(booking, by_user)` | RESERVE | Allowed to the **requester or any curator** of the reservations collection (`Thing.can_manage`, 2026-09; rule 4), only while `start_date >= today` — and, for an `HOUR`-unit reservation, only until its `start_time` on that day (2026-09-18: cancelling this morning's slot this afternoon would free, and announce, something that already happened; "today"/"now" are the deployment's `TIME_ZONE`). Sets `CANCELLED` under a lock, then fans `RESERVATION_CANCELLED` (in-app + email) to everyone who didn't cancel — the member (if a curator did it) and every other manager — **and separately gives `by_user` their own cancellation confirmation** (email: `send_reservation_cancel_confirmation_email`, 2026-09-28, closing the gap where the member's earlier "your reservation is confirmed" email was the last word in their inbox on a reservation that no longer stood; in-app too since 2026-09-29: the reservation's whole story lives in the inbox, and the canceller's copy is a `by_you` record in the first person, carrying `member_name` when the reservation was somebody else's). `other_name` / the email's `{other}` is always **whoever actually cancelled**; `cancelled_by_owner` (→ the email's "your reservation" wording) is set only on the member's copy. |

##### The request notification's lifecycle

`BOOKING_REQUESTED` is a **question put to the whole team that runs the thing** — accept or reject? — so it must not outlive its answer. `send_booking_request_notifications` writes one copy per manager (`thing.managers()`, never the requester), and `_clear_request_notifications(booking)` deletes **every** copy, matched by `payload__booking_code` and deliberately not by user, so a co-curator's copy goes whoever settled the request. It is called from every path that settles a request:

- `finalize_booking_decision()` on success — **both** accept and reject, and it is the single convergence point of the email/RSVP path (`VerifyLinkView`) and the in-app path (`BookingActionView`), so one call covers both. (The reported bug: accepting from the email left the notification sitting there.) Its `decided_by` parameter (the in-app path passes `request.user`, the emailed link whoever the link was minted to — `rsvp.user_code`, whose authority `VerifyLinkView` re-checks at the click) is who the requester's notice names as `owner_name` — a co-curator's decision is signed by the co-curator, not read as the founder's. After the clear it also leaves a `BOOKING_DECIDED` record with **the rest of the team that runs the thing** (`_notify_team_of_decision`: `thing.managers()` minus the requester **and minus the decider**) — the request was a question put to the whole team, so the answer reaches the others (2026-09-29); whoever decided is not told what they just did (2026-10-02: "You confirmed…" cards were three of five in one inbox — it used to leave them a `by_you` trace). The clear is type-scoped, so the decision record — same `booking_code`, different type — survives it.
- `cancel_booking()` — the requester withdrew; the team has nothing left to decide.

The payload keys that make this work (`booking_code`, `thing_code`, `collection_code`) are documented under [`InAppNotification`](../models/CLAUDE.md#inappnotification). Notifications created before those keys existed simply never match the filter and stay until dismissed by hand.

#### Patterns

- **Snapshots, not lookups**: both `request_*` functions copy the thing's `type` **and** its `deposit` onto the booking (`thing_type`, `deposit_amount`). The reservation is a record of what was agreed, so editing the listing afterwards cannot rewrite it — and since `accept_booking` always attaches the booking to the `ThingTransfer` it creates, the journey reads the agreed amount through `transfer.booking` rather than keeping a second copy that could disagree.
- **Atomic transactions**: Every function wraps its work in `transaction.atomic()` to ensure `BookingPeriod` and `Thing` are updated together or not at all.
- **Row-level locking**: Uses `Thing.objects.select_for_update()` to prevent race conditions when two concurrent requests try to modify the same thing's status.
- **Single-use type check**: Only GIFT and SELL things (`SINGLE_USE_TYPES` from `core.models.booking`) change thing status on accept/reject/cancel. Date-based types (LEND, RENT) leave thing status unchanged because multiple bookings can coexist.
- **`is_endless` guard**: For GIFT/SELL things where `thing.is_endless=True`, all status changes (TAKEN on request, INACTIVE on accept, ACTIVE on reject/cancel) and ThingTransfer creation are skipped. The thing remains ACTIVE at all times and accumulates multiple simultaneous PENDING bookings from different users. `expire_old_pending()` also excludes endless things from the TAKEN→ACTIVE restore.
- **Thin view, service raises**: the reservation-request business logic lives entirely in the `request_*` functions. `ThingRequestView` only does HTTP-layer work — shared guards, serializer parsing, response shaping — and translates `BookingRequestError` into the `{"error": ...}` response. Callers outside DRF (management commands, future flows) can request bookings without touching the view.

### Rules of a network's things (`Collection.rental_rules_for`, `effective_text`)

`booking_service.request_date_based_booking` asks `rental_collection.rental_violation(start, end, owner_code=thing.owner_id)`, `Thing.availability_window` reads `collection.rental_rules_for(owner_id)` and `ThingSerializer` serves the same answer (`rental_weekdays`, `closed_dates`, and the notes through `effective_text`), so the server's refusal, the card's live availability and the request page's pickers cannot disagree (`test_network_effective_rules.py` walks 45 days comparing the payload with the refusal). `resolve_rental_collection` returns a network even when the collection itself sets no rule, because its pickup points carry theirs. `receives_booking_requests` adds the founder of a NETWORK: they reject pending requests as a rescue before having uploaded a thing.

### `email_service.py` — Centralised Email Sending

All outbound emails are composed and sent from this module. Views call these functions rather than constructing emails inline.

#### Categories and notification preferences

Every email belongs to one of three categories. Each function routes through the internal `_send()` helper, which checks the recipient's preferences (looked up by email on the `User` model) before dispatching.

| Category | Constant | User flag | Scope |
|----------|----------|-----------|-------|
| **Cat. 1 — Mandatory** | `CATEGORY_MANDATORY` | (ignored — always sent) | `send_magic_link_email`, `send_collection_invite_email`, `send_collection_welcome_doc_email`, `send_collection_revoke_email`, `send_account_delete_email`, `send_inactivity_warning_email`, `send_email_note_test_email` (a curator's own test of their email note — asked for that moment, so an activity opt-out must not swallow it) |
| **Cat. 2 — Activity** | `CATEGORY_ACTIVITY` | `User.notify_activity` | `send_booking_request_email`, `send_booking_decision_email`, `send_booking_confirmation_email`, `send_reservation_confirmed_email`, `send_reservation_notice_email`, `send_reservation_cancelled_email`, `send_reservation_cancel_confirmation_email`, `send_reservation_reminder_email`, `send_invite_rejected_email`, `send_faq_question_email`, `send_faq_answer_email`, `send_faq_answered_to_team_email`, `send_faq_hide_email`, `send_faq_hidden_to_team_email`, `send_thing_reported_email`, `send_return_reminder_email`, `send_return_due_email`, `send_return_overdue_email`, `send_broadcast_email`, `send_join_summary_email`, `send_invitation_proposal_email`, `send_proposal_declined_email` |
| **Cat. 3 — News** | `CATEGORY_NEWS` | `User.notify_news` **and** `Collection.digest_muted` | `send_digest_email` |

**Both flags default to ON, and Cat. 3 has a second, narrower switch.** `notify_news` used to default to `False`, which — combined with `Collection.digest_frequency` defaulting to `NONE` — meant the digest reached almost nobody: an owner had to find a setting buried in an accordion *and* every reader had to have opted in to a toggle labelled "optional". Both now default on, together with the control that makes it honest rather than a pre-ticked opt-in (DESIGN §6): **`Collection.digest_muted`**, a per-group mute.

- A member silences one group without losing anything else — the booking, question and reminder emails are Cat. 2 and untouched. There is no "all or nothing" any more.
- Two ways out, both one click: the entry in a member's collection menu ("Mute the summary"; `is_digest_muted` on `CollectionSerializer`, `POST /collections/{code}/digest/`) and the link in the footer of the digest itself (`POST /digest/mute/{token}/`, no login — see the signed tokens below).
- **The mute is scoped to CATEGORY_NEWS only.** `_should_send`/`_filter_recipients` take a `collection` and consult it for news alone, so silencing a chatty group never suppresses the notice that your own hold there was confirmed.
- If the mute is ever removed, `notify_news` has to go back to defaulting `False` — pinned by `test_new_user_starts_subscribed_to_both_categories`.

- **Lookup fallback**: if no `User` matches the recipient email (e.g. a not-yet-registered invitee), `_should_send` returns `True` — all emails reach non-users by default.
- **Multi-recipient**: functions that take `emails=[...]` (digest, broadcast) use `_filter_recipients()` for a bulk query that drops opted-out addresses before iterating. `_send_per_language` also accepts an **`extra_footer(user, lang)`** hook for a line that must be built *per recipient* rather than per language — the digest's mute link carries a token signed for one user, so it cannot join the language-cached body.
- **Preferences footer**: Cat. 2 and Cat. 3 emails get an auto-appended footer with a link to `/me/notifications/{token}` (see below). Cat. 1 skips it — nothing to manage. **Separately, every category including Cat. 1 gets a legal footer** — see the art. 14 note below, which is not preference-gated because it is a disclosure duty, not an opt-out.
- **Viral CTA**: every send except the operator's own ops mail (which passes `include_viral=False` — a report, not growth copy) prepends one growth blurb above the footer — by default a random one from the per-language `VIRAL_LINES` catalogue (`email_texts/{lang}.py`, read via `viral_lines()`), or, when a deployment sets `VIRAL_LINE_PROVIDER` (a dotted path to `provider(user, lang) -> {"text", "cta", "path"} | None`, see `SELF_HOSTING.md` §5), the one that function picks for that recipient: asked **after** the suppression below and never for someone who curates a collection, `None`/an incomplete answer/a `path` that does not start with a single `/` means no line, a raise means no line plus a `logger.warning` naming the setting (never the recipient), and `core.E006` fails the deploy on a path that does not import or is not callable — the CTA is the plain `{frontend_base}{path}` link, never tracking-wrapped (DESIGN §9): each line carries a `path`, the form of the kind it talks about (`/stall/new`, `/library/new`) or the chooser `/new` for a line about none in particular, which is also where a line with no `path` leads; the same destinations in the three languages (`test_email_language.py`). It is suppressed for recipients who already own **or co-curate** ≥1 collection (2026-09-28: since 2026-09 a co-curator has the founder's whole reach minus deleting the group, so the line was an invitation to start what they already run — in production the FAQ notice reached the co-curator with it and the owner without; the `_curates_collection` flag is one `Exists` over `owner` OR `co_owners`, folded into the existing `_lookup_user`/`_lookup_users` query — no extra round-trip), and for an empty list. So the bottom order is always: body → viral line (when shown) → preferences footer (when present). **`send_magic_link_email` carries it too** (the magic link is the one email every user gets, so suppressing growth copy there starved the loop) — this makes `_send()` do one extra `User` lookup for magic-link sends it used to skip, but both its callers only ever reach it after the recipient is already resolved (`RequestLinkView` for a confirmed-registered address, `JoinView` after `get_or_create`), so the lookup adds no new registered/unregistered timing signal (the one timing delta that remains is about language resolution, not this gate — see below). **Styled as a highlighted callout**: a pale-yellow background (`#FFF1A8`) and `padding:10px` set it apart from the plain grey footer prose around it, and its own text is black (`#000000`) rather than the footer's muted `#888888` — only the CTA link inside keeps the link style's accent colour (`email_style()['link_style']`). Pinned by `test_the_viral_line_is_a_pale_yellow_callout_with_black_text` (mutation-tested: reverting the style drops the test).

#### The legal footer (art. 14 GDPR) — every email, no exceptions

`_render_email()` (the shared HTML renderer every sender's `html = _render_email(...)` goes through) always injects a link to `{frontend_base}/legal`, rendered by `core/templates/email/layout.html` after the last content block. Unlike the preferences footer above, this one is **not gated by category** — an unsubscribe link is a courtesy the recipient can decline; a controller's identity and the terms under which their data is processed are not. `lang` (the same value senders already thread through `T`/`L`) picks the label's language via the `footer_legal` key; a caller that omits it falls back to the deployment default, same as `T()` everywhere else.

**`send_collection_invite_email` carries a second, specific disclosure** (`invite_source_note`, all three catalogues): the invitee's address didn't come from them, it came from whoever invited them, which is exactly the case art. 14 exists for. The sentence says where the address came from, what it's used for, and that declining or ignoring the email means that person cannot invite them by email again for a year — appended to **both** the HTML blocks and the plain body, since this is the one email in the catalogue sent to somebody who never asked OIUEEI for anything directly.

**`<html lang="...">` itself follows the same resolved language**: `_render_email` computes `lang or EMAIL_LANGUAGE` once and passes it to the template as `lang`, so a screen reader pronounces the body in the language it's actually written in rather than whatever the browser/client's own default assumes. Every email already speaks a specific, known language by the time it's composed (`resolve_email_language`), so this was never genuinely unknown — only unstated.

#### Email language — the hierarchy (`EMAIL_LANGUAGE` + `Collection.language` + `User.language`)

Which language an email speaks is decided per **recipient**, by three levels, weakest to strongest:

1. **Deployment default** — `EMAIL_LANGUAGE` (env var, default `en`; the standalone repo stays English, a deployment sets its own).
2. **The collection's language** — `Collection.language`, the owner's choice for their group.
3. **The recipient's own preference** — `User.language`, which always wins.

Blank means "inherit", so a level only speaks when it was actually set — existing rows keep the old per-deployment behaviour with no data migration. `resolve_email_language(user=None, collection=None)` implements it; `_recipient(email, collection=None)` resolves the recipient's `User` **once** and returns `(user, lang)`, handing the user to `_send()` so the preference check, footer link and viral gate don't re-query it.

Senders **shadow the module-level `T` with a language-bound one** (`T = _texts(lang)`), so every `T("key")` in the body speaks the recipient's language without threading the argument through each call. `_send(..., lang=)` follows it for the footer and viral line, so the whole message is in one language.

Senders bind **`L = _local(lang)`** next to `T` and pass every **owner-written** value through it — a collection headline, a thing headline (either of them may carry one text per language as inline JSON). So the resolution happens exactly where the recipient's language is already known, and a Catalan member reads "…a 'Les coses de mama'…" while their Spanish neighbour reads "…a 'Las cosas de mamá'…" from the same row. A plain headline — nearly all of them — comes back untouched. The operator-facing senders carry aggregate numbers, not owner content.

- **Collection-scoped emails pass their collection**: invite (+ bulk), invite-rejected, revoke, welcome-doc, broadcast, digest, and the join magic link.
- **Thing-scoped 1:1 emails pass only the recipient** (bookings, FAQs, reminders, reports): there is no group to speak for, so it's their preference or the deployment default — never a guessed collection.
- **Bulk sends compose per language**: `_send_per_language(emails, category, compose, collection=...)` drops opt-outs, bulk-resolves the users in one query, and calls `compose(lang)` once per *distinct* language among the recipients — so one digest to a bilingual group leaves in two languages while a 50-member single-language group still composes once.
- **The magic link is the exception**: its caller (`core/views/auth.py::_send_magic_link`) resolves the language and passes it in, because that sender must not look the recipient up — `request-link` only sends for a registered address, so a DB round trip would make "registered" responses measurably slower and become an email-enumeration timing oracle.
- **`JoinView` never takes a `language` from the request** — it used to, stamping it onto a **newly created** user's `language` so their first magic link would speak their current UI language. That stamp was permanent: an accidental browser language, never a deliberate choice, then outranked the joined collection's own language for every future email to that member, with no way back short of a profile edit. A new joiner's `language` now stays blank, so this hierarchy's own second level — the collection's language — governs their first email exactly as it does every later one.

Every user-facing string lives in a per-language catalogue — `email_texts/en.py` (the reference + universal fallback), `es.py`, `ca.py` — as flat `TEXTS` dicts of `str.format` templates, mirroring the `seed_data/{lang}.py` pattern. `T(key, lang=None)` falls back to English for an unknown language or a missing key; without `lang` it reads `settings.EMAIL_LANGUAGE` on every call (so `override_settings` works in tests). `test_email_language.py` pins the en default, the es/ca deployments, the fallback, and en↔{es,ca} catalogue/placeholder/viral-line parity (the email analogue of `i18nParity.test.js`); `test_email_hierarchy.py` pins the resolution matrix and the per-recipient bulk sends. To add a language: copy `en.py` → `{lang}.py`, translate only the values (keep keys + `{placeholders}`), and add the code to `Language` in `core/models/language.py` so owners and users can pick it. The operator-facing senders (the capacity alarm) carry data, not copy, and are not part of the catalogue.

#### Signed tokens for unauthenticated preference editing

- `make_notifications_token(user_code)` — returns a `TimestampSigner`-signed string (salt `notifications-prefs`, TTL 1 year) scoped to notification preferences editing.
- `verify_notifications_token(token)` — returns the user_code on success, `None` on failure.
- `make_digest_mute_token(user, collection)` / `verify_digest_mute_token(token)` — the digest footer's one-click unsubscribe. Signs `{user_code}:{collection_code}` under its **own salt** (`digest-mute`), so it can't be swapped for a preferences token either way. Same 1-year TTL, same reasoning. Blast radius: one row in one M2M, undoable by the member from the collection page. Consumed by `DigestMuteByTokenView` (`POST /api/v1/digest/mute/{token}/`) — **POST, never GET**, so a mail client's link scanner or a prefetch can't unsubscribe somebody; the SPA page at `/digest/mute/:token` fires it from JS, which a scanner never runs.
- Used by `NotificationsByTokenView` at `GET/PATCH /api/v1/notifications/token/<token>/` so recipients can toggle preferences via the email footer without logging in.

**The 1-year TTL is deliberate, and was reviewed as such** (don't re-flag it without reading `_PREFS_TOKEN_MAX_AGE`). It looks like a token that should expire fast: it rides in a URL path, in the footer of every Cat. 2 / Cat. 3 email, and authenticates without a login. But stolen it can flip exactly two booleans — nothing to read, nothing to spend — while expired it breaks the link somebody clicks *to stop receiving email from us*. That is the unsubscribe link whatever the page calls it, and a dead one turns withdrawing consent into "log in, find the profile editor, scroll to preferences". The long TTL is the user-protective side of that trade, not the lax one. Rotating `SECRET_KEY` invalidates every outstanding token at once, which is the revocation path that matters.

#### Patterns

- **XSS prevention**: All user-provided content is escaped with `django.utils.html.escape()` before being inserted into HTML email bodies. Plain text versions use raw values (safe in plain text context).
- **The owner's email note (`Collection.email_note`) is the one hand-built HTML in a body** — rendered by `_note_blocks` into a single `md` block that `layout.html` emits verbatim (`{{ b.html }}` arrives `mark_safe`d; every other block is autoescaped). Its invariant, the backend twin of `MarkdownText.jsx`'s: **escape() every line ONCE, up front; `_md_inline` never escapes again** (a `&` in a link's URL would double-escape into a different address) — and NUL is stripped in both places so typed text can't forge the anchor placeholder. Subset: paragraphs (`\n` alone → `<br />`), `-`/`1.` lists, `**bold**`, `*italic*`, `[text](url)` — http(s), `www.…` (read as `https://www.…`) and `mailto:`, the url taking **balanced parentheses** (`…/wiki/Foo_(bar)` is not cut at the first `)`); an unsafe scheme (or a URL with no host) stays as literal text (a dead `href="#"` confuses more than the raw link), and **a link whose text isn't its own URL is followed by its real host**, in punycode (`carnet (your-domain.test)`): these emails leave from the operator's domain and the owner picks both halves of the link, so `[https://www.your-domain.test/verify/…](https://elsewhere.example)` must not read as the operator's own sign-in link; no headings or tables (a ≤512-char note doesn't carry document hierarchy, and that voice is the layout's). The plain-text half carries the **raw Markdown**, the standard shape for a text/plain alternative. It rides the requester's emails only (`send_reservation_confirmed_email`, `send_booking_confirmation_email`, and the **accepted** branch of `send_booking_decision_email` — never a refusal, which has no next steps for the note to describe) and never the owner's own notices — resolved per recipient via `L` and placed after the listing link, before the legal footer, with no positional logic (block order is the position). Deliberately no `email_texts` label ("A note from the group:"): the note is owner prose and reads as the email's closing line.
- **Nobody is named to a stranger by their address**: `User.display_name` falls back to the email, and `name` is empty for **every** account made by `get_or_create(email=…)` — everyone who arrived by magic link or invitation and never filled in a profile. So the fallback is the ordinary state of a new member, not an exotic one. Callers pass the **bare `name`** and `_member_name(name, lang)` substitutes the localized `a_member` ("A member" / "Un miembro" / "Un membre") where the copy interpolates it mid-sentence; where the name has a line to itself the caller drops the line instead (`proposer_name`). `display_name` survives only where the reader already holds the address — a collection owner (`owner_member_rows`) or a thing owner reading a request (`BookingPeriodSerializer.requester_email`, which the "Requests to me" page shows as a link) — plus the operator's own ops mail. **The requester's address in the request and reservation emails to each manager is the same exception**: the reader is whoever manages the thing and reads that address in the app; it never flows the other way. The in-app payloads follow the same rule and the SPA fills the gap with `common.aMember`. Pinned by `core/tests/integration/test_member_name_privacy.py` and `test/inboxNotifications.test.jsx`.
- **The card, and one fixed footer order — `_render_email` / `_bottom()`**: every message is a white, rounded box (`max-width:600px`, `1px solid #DDDDDD`, `10px` radius, `32px 24px` padding — the border colour was corrected the next day, from `#888888`; only the outer page’s own padding was specified, not the card’s, so `32px 24px` is this implementation’s pick) on a `#F9FAFB` page with `40px` padding. The card’s **top half** — the `<h1>` parent and the body blocks — is what `_render_email()` renders through `layout.html`, which opens the two wrapping `<div>`s and deliberately never closes them (see the comment at the top of that file). The **bottom half** — a `<hr>`, the OIUEEI mark, the viral line, "manage your preferences", a sender-specific extra line (the digest’s per-collection mute), always last the legal link, then the two closing `</div>`s — is built in Python by the new `_bottom()` (replacing the separate `_with_viral_line` + `_with_footer`) and appended **once per actual recipient** inside `_send()`. That split — one HTML element opened in a template and closed in a string concatenation — exists for one reason: a digest or broadcast composes its card **once per language** and reuses it for many people, but the footer still has to differ per person (a collection owner gets no viral line; Cat. 1 mail gets no preferences link) — so the closing tags have to travel with the part that is genuinely per-recipient. `_send()` grew an `extra_footer` parameter to carry this (previously `_send_per_language` spliced it in by hand before calling `_send`). Pinned end-to-end by `test_send_test_emails.py::test_every_email_is_the_white_rounded_card_on_the_grey_page` and `_assert_the_footer_order` in `test_email_service.py`. **Both containers give up their framing below 480px** (seen in the Gmail iOS app): the page's 40px padding plus the card's own 24px stack to ~64px lost from each side on a phone screen, shrinking the reading column to almost nothing. A `@media only screen and (max-width: 480px)` block in `layout.html`'s `<style>` (same place as the button-hover rules) drops the grey/white split, the border and the radius, leaving the page `<div>` (`class="oiueei-email-page"`) as the only, much smaller (16px), source of padding, and the card `<div>` (`class="oiueei-email-card"`) full-width with none of its own. Every rule needs `!important` — a plain stylesheet rule, media query or not, loses to the elements' own inline styles, and only an `!important` author rule outranks inline. Progressive enhancement, same reasoning as the hover rules: a client that drops `<style>` keeps the desktop layout, cramped but not broken. Pinned by `test_the_card_and_page_shed_their_padding_below_480px` (mutation-tested). **Buttons go full width in the same breakpoint**: `.btn-primary, .btn-secondary { display:block; width:100%; box-sizing:border-box; text-align:center; margin:0 0 12px 0; }`, all `!important` — a button sized to its own label read narrower than the paragraphs either side of it once the card's own padding was gone too. `box-sizing:border-box` keeps the buttons' existing padding (`email_style()['btn_primary']`/`['btn_secondary']`) from pushing the box past 100%; the `ctas` pair's side margin (`margin:0 12px 12px 0` on the primary, for the desktop side-by-side layout) is zeroed here too, or a 100%-wide box plus that margin would overflow past the text's own right edge. Pinned by `test_buttons_go_full_width_below_480px` (mutation-tested).

The collection is now, in order: **the `collection` the caller passed** (it resolved it *for this reader*: `send_booking_decision_email` and `send_booking_confirmation_email` get it from `resolve_request_collection(..., requester)`, `send_reservation_confirmed_email` is handed the reservations collection, where the requester is a member); else **the first of the thing's collections, by code, that `reader` can open** (`Collection.can_view`, with the reader's memberships settled in **one** query for the whole list — `_first_collection_readable_by`, the shape of `booking_service._readable_collections` — never an `is_invited` per collection); else **none**, the bare `/things/{code}` route. A call with no `reader` (an address with no account) gets the bare route too: a collection nobody has checked for the person reading is never named. **All ten senders that link a thing pass `reader=user`** (the `User` their `_recipient(...)` already resolved), and a table test runs every one of them against a private group whose code sorts first, so a new sender that forgets is caught. Measured cost per email: **1 query on a path that prefetched the thing's collections** (the membership query, replacing the old `.first()`, which cost one even then — an ordered clone discards the prefetch cache), **2 when it did not** (the list as well, one more than before, per recipient and never per collection), and **0 for an address with no account**. `_thing_collection` — still the note's fallback in `send_reservation_confirmed_email` when no collection is passed — is **not** reader-checked and no longer what `_thing_url` uses.
- **Action links**: Booking and invitation emails include accept/reject links (RSVP-based URLs generated by the calling view). FAQ question emails include a direct link to the thing page, and so does the booking **decision** email — that one reaches the requester at the end of their flow, so it has to lead somewhere; it reuses `view_thing_cta` rather than adding a fourth way to say "view the listing". The decision email also carries **one subject per outcome** (`decision_subject_confirmed` / `decision_subject_cancelled`): a single subject for both an accepted and a refused hold cannot be read from an inbox. The word in the body for the refused outcome (`decision_cancelled`, interpolated into `decision_intro` and the two `decision_plain*` sentences) is **"rechazada" / "rebutjada" / "declined"**: the manager declines a request, nobody cancels it, and "cancelada" read as though the requester had; the key keeps its old `_cancelled` name, as `hold_cancel_cta` does.
- **The `cta` block — an email's one action as a button, every one, with its own link repeated as text below it**: `_cta(url, label, fallback)` renders an inline-styled `<a>` in the app's own palette as **literal hex** (`color_01` fill, `color_06` label) plus the `fallback` sentence and the raw URL as copy-pastable text under it. Not a `<button>` and not a CSS custom property: email clients strip forms and buttons outright (Gmail) and none of them resolves `var()`, so the app's primary button can only travel as a styled link. **The fallback link now applies to every single-action email, not only the ones whose whole job is one click** — the lighter `_button(url, label)`, which drew a bare button with no fallback sentence or link, is deleted; every one of its ~13 call sites now goes through `_cta` with the shared `cta_fallback` catalogue key (renamed from `magic_fallback`, whose wording was already generic).
- **The house rule for email buttons** — decided once so it is not reopened per email: the **primary action** of an email (sign in, open the group, look at the thing, open the document) is a **primary button**, never a bare text link; and where an email asks a yes/no question, the **positive answer is the primary button and the negative the secondary one**. Two builders carry it now (a third, the lighter no-fallback `_button`, was folded into `_cta` the next day — see above), both through one pair of style constants (`BTN_PRIMARY` / `BTN_SECONDARY`, handed to `layout.html` by `_render_email` so the blocks cannot drift): **`_cta`** (one action, every single-action email) and **`_ctas`** (the yes/no pair — invitation, hold request, proposal). **`_links` now has NO callers at all** (2026-09-22) — the account-erasure confirmation was the one deliberate exception ("a destructive step is not obviously the place for the app's friendliest control"), until it was made a button too; `send_account_delete_email` now uses `_cta` like everything else, the same blue as every other button (no new "danger" colour). `test_email_service.py::test_no_email_action_is_ever_a_bare_text_link` reads the source and fails the moment any email reaches for `_links` — a new email cannot quietly break the rule. Two emails that used the thing's *headline* as their link text (`send_booking_confirmation_email`, `send_faq_answer_email`) now say `view_thing_cta` on a button instead — the headline is already printed just above it.
- **The `ctas` block — two answers as a primary and a secondary button (the collection invitation and the owner's hold request)**: `_ctas((url, label), (url, label), fallback)`, the two-answer sibling of `_cta`, for the emails that ask a yes/no question: `send_collection_invite_email` (accept / decline) and `send_booking_request_email` (confirm hold / cancel hold, to the thing's owner). One more email has the same accept/reject pair and is still a plain `links` row: `send_invitation_proposal_email` (the owner approving a member's suggested guest). Accepting is the **primary** button (the same filled anchor as `cta`), declining the **secondary** one — white fill, a `2px solid` accent border and an accent label, the app's own split (its padding is two pixels short of the primary's on every side, so the border brings both to the same outer size). Both raw URLs follow as text, accept first, after a `fallback` sentence (`ctas_fallback`, one key shared by both emails, all three catalogues — a missing key is a `KeyError` at send time, which the parity test catches). It replaced a `links` row, `Accept | Decline`, two text links of equal weight. On the invitation the block sits before the art. 14 `invite_source_note`, which stays the last thing the message says. The plain-text half is unchanged: it always carried both links. Pinned in `test_email_service.py` for **each** email (primary/secondary styles and order, both links spelled out, the fallback and labels translated) — each goes red with the old `links` row put back.
- **`from_email=None`**: Uses Django's `DEFAULT_FROM_EMAIL` setting.
- **Booking email variants**: `send_booking_request_email` and `send_booking_decision_email` adapt their content based on booking type — date-based (start/end) or simple (no extra fields).
- **Dates render DD/MM/YYYY**: `_fmt_date(value)` (accepts a `date`/`datetime`, an ISO string, or `None`→`""`) formats every date a reader sees in an email — booking/reservation start-end, the `dates_label` field, the return-reminder `{end}`. **A single day is said once (a loan confirmation read "Fechas: 13/10/2026 - 13/10/2026")**: `_fmt_dates(start, end)` builds the `dates_label` value (one date when both are the same, `start - end` otherwise — hour-unit reservations keep their range), and in the three booking emails' plain text `_when_phrase` picks the `when_range` ("del {start} al {end}" / "from {start} to {end}") or `when_day` ("el {start}" / "on {start}") catalogue phrase that the `*_plain_dated` templates now take as `{when}`. The reservation emails' plain-text sentences take the same phrase as `{when}` (`_phrase_for`, from `_fmt_when`'s pair), so a one-day reservation reads "el 05/10/2026" and an hourly one keeps "del 05/10/2026 10:00 al 13:00". A plain `str(date)` gives ISO `YYYY-MM-DD`, which read one way here and another in the SPA. The catalogue templates just interpolate `{start}`/`{end}`, so the format lives entirely in `email_service`. The **operator** capacity alarm keeps `collection.created.isoformat()` — a full timestamp on an ops/audit line, not user-facing.
- **`_fmt_when(booking)`** is the one difference an `HOUR`-unit RESERVE_THING makes to the four reservation emails (`send_reservation_confirmed_email`, `_notice_email`, `_cancelled_email`, `_reminder_email`) — each already reads `{start}`/`{end}` into `"…to…"` / `"del…al…"` templates and `dates_label`'s `f"{start} - {end}"`, so no catalogue string changed in any of the three languages. Whole-day (`start_time` NULL — every `DAY`-unit RESERVE; these four are never sent for LEND/RENT) returns the start and the reservation's **last day, inclusive** (`end_date − 1`): `end_date` is `start + duration`, the day the space is free again — right for overlap checks and the calendar export (Google's all-day End Date is exclusive too), wrong as the end of the member's booking. It used to print it as-is, so a one-day reservation on the 5th was "confirmed for 05/10 to 06/10". A one-day reservation now reads "05/10/2026 to 05/10/2026". An hourly booking returns the date once, on `start` (`"05/10/2026 10:00"`), then just the end clock time (`"13:00"`) — a second date would be redundant since both are the same day.
- **The reservation notice says a contact phone was left, never which** (`reservation_notice_phone`, one line in the three catalogues, only when `booking.contact_phone` is set): the number lives in the app until the day after the booking and `purge_expired_data` then empties it, which a copy in a mailbox would outlive. `send_test_emails` shows the line.
- **Reservation emails** (`send_reservation_*`): auto-confirmed, so the requester reads "confirmed", not "request sent"; the **notice** (`send_reservation_notice_email`) goes to **every manager** of the thing (2026-09, `Thing.managers` — the team runs the space together), carrying the `project_note` (escaped) when present **and the requester's own email address** (a manager reading "Lele reserved" had no way to actually reach Lele; `requester.email` as a `_field(..., email=True)` block, bus blue and a real `mailto:` link) — legitimate to show here despite the no-address rule, since a RESERVE_THING requester is always a collection member by the time this fires and the manager reads the same address in the app (`BookingPeriodSerializer.requester_email`, a link on "Requests to me"). **It sets `Reply-To` to the requester's address** (and says nothing about it) — the same `_requester_contact` as the request email; the label is the generic `requester_email_label` (it was `reservation_requester_email_label`, renamed in the three catalogues now that the request email shares it); the **confirmation** (`send_reservation_confirmed_email`) says where the requester will be written to — `contact_shared_reservation`, "Your email goes with the booking." (deliberately shorter than the one in the "request sent" email, which keeps the longer "…: if needed, they'll write to you here, at the address you sign in to OIUEEI with."), after the fee and the place, before the button; the address itself is not printed; the cancelled one picks "your reservation" vs "their reservation" by `cancelled_by_owner`, which the fan-out sets true only on the member's copy. **Cancelling also mails the person who cancelled their own confirmation** (`send_reservation_cancel_confirmation_email`, 2026-09-28) — the fan-out above tells everyone *else*, by construction, so without this the member's own "your reservation is confirmed" stayed the last word in their inbox after the reservation was gone; no button and no `email_note`, since there is nothing left to act on, and — since 2026-09-29 — an in-app `by_you` record for the canceller as well, whose first-person copy carries `member_name` when the reservation was somebody else's. The **reminder** (`send_reservation_reminder_email`, `start_date` = tomorrow, via `send_reminders`) is the arrival nudge — requester-only, since nothing is carried. RESERVE does not use the three generic booking emails, nor the return reminder.
- **Per-type action nouns**: the three generic booking emails (request/confirmation/decision) interpolate `{action}` from `_action_noun(thing)` (`T(f"action_noun_{thing.type}")`) so the wording mirrors the frontend's per-type vocabulary — a SELL request reads "purchase request" / "solicitud de compra", a LEND request "loan request" / "solicitud de préstamo", etc. Five nouns live in each catalogue (`action_noun_{GIFT,SELL,LEND,RENT,RESERVE}_THING`) — one per type; the `test_every_bookable_type_has_an_action_noun` guard iterates `Thing.Type.values`, so a new type needs one even if (like RESERVE) it never reaches these emails. A missing key would be a `KeyError` mid-decision, after the booking already committed. **Catalan caveat**: in `ca.py` the noun values carry the preposition (`"de compra"`) and the templates read `sol·licitud {action}` — Catalan elides "de" before a vowel, so the en/es template shape (`de {action}`) can't work there; a new type starting with one needs `d'` in the value. The owner confirm/decline button verbs (`hold_confirm_cta`/`hold_cancel_cta`) stay generic by design — and say **request**, not reservation ("reservation" is only RESERVE_THING, which confirms itself and never comes through this email): "Confirmar la solicitud" / "Rechazar la solicitud", "Confirmar la sol·licitud" / "Rebutjar la sol·licitud", "Confirm request" / "Decline request" (the second used to read "Cancelar la reserva" though it rejects, as the app's own button already did); the plain-text `booking_request_plain*` lines repeat them. The key keeps its old `_cancel_` name.
- **Reply-To header**: `send_broadcast_email()` uses `EmailMultiAlternatives` with `reply_to` so invitees can respond directly to the collection owner (routed through `_send(..., reply_to=[owner_email])`). The visible body links to the collection (`/{kind}/{code}`) — the object that originated the message — rather than promising an email reply. **The owner is told before they send**: the broadcast box's helper line says that whoever receives it can reply directly and will see their address (`broadcast.replyToNotice`). It is the one place in the product where a member learns an address the API takes care never to serve them, and it is the owner's own — so the answer is disclosure, not a switch: dropping the header would turn a group message into a megaphone whose replies land on a noreply.
- **Digest emails**: `send_digest_email()` lists new thing headlines in both plain text (bulleted) and HTML (`<ul>/<li>`) formats.
- **Direct collection links**: a collection is linked at its kind's address, `{frontend_base}/{kind}/{code}` (`Collection.path()`; `_collection_path()` in `email_service` takes the collection the caller holds — the broadcast and the digest always pass it — or reads its kind in one query per send, never per recipient, and falls back to the old `/collections/{code}`, which the server redirects). A thing is linked as `{base}{collection.path()}/things/{code}` (`_thing_url`). `send_digest_email()` links straight to the collection. Per DESIGN.md §9 we do not track email engagement — links are never wrapped in a redirect or tracking pixel.

#### The digest — what it says today, and what it could say

The digest is the one message that reaches a member **between** their own events: every
other email answers something they did (a request, a question, a reminder), so for most
members it is the whole of what brings them back to a group. That makes its content a
product decision, written down here so the next change to it starts from the same page.

**What it sends today** (`send_digests` → `send_digest_email`):
- **When:** the daily scheduler job runs it; it acts on Mondays for `WEEKLY` collections
  (the 7 days before) and on the 1st for `MONTHLY` ones (the month before). `digest_frequency`
  defaults to `WEEKLY`; `NONE` sends nothing.
- **What:** the headlines of the things **created** in that window that are `ACTIVE` or
  `TAKEN`, as a list, then — only when there is someone — one line with **how many people
  joined the group in the same window and still belong to it** (`digest_new_members_one` /
  `_other`: "And 3 new people joined the group."), then one button to the collection.
  The count is `MEMBER_JOINED` events of the collection in the window, distinct people,
  intersected with today's `invites`: **a number, never names** (the digest reaches every
  member, and a list of names would hand out the member list), **nothing with 0**, and
  **departures are never mentioned**. One query per collection, not per recipient. It
  rides only the digests that already go out: a group with no new things still sends none.
  Headlines resolve per reader's language. Nothing else: no questions, no handovers.
- **Whom:** the whole team: every member (`invites`, which holds the co-curators) **and the
  founder**, once each, except those with `notify_news` off or who muted this group
  (`digest_muted`). The founder's footer link and the muting work as for anyone.
- **Skipped** when nothing was created in the window, or the group has no members (`invites` empty:
  the founder alone would be told what they added themselves). A quiet
  group therefore sends nothing at all — honest, but it also means a group whose life is
  loans rather than new things never reaches its members this way.

**What a good digest would add** — candidates, none built; each must pass DESIGN §9 (would a
member be surprised to read it, and does it say anything about a person they could not
already see in the app?):
- **Questions answered** on the group's things in the window — the question and the thing,
  never who asked (the app shows the asker's name only on the thing's own page).
- **What comes back soon** — things on loan or rent in this group due back in the next
  days, so a member waiting for one knows; by thing, never by borrower.
- **Nothing new is not nothing:** with no new things but some of the above, send; with none
  of it, keep skipping — a digest that says "nothing happened" teaches people to ignore it.

Any of these changes `send_digests`' selection, `send_digest_email`'s compose, the three
`email_texts` catalogues and `test_commands.py::TestSendDigestsCommand`.
- **Preference pipeline**: every send goes through `_send()` → `_should_send()` + `_bottom()` (the viral line, the preferences link and the legal link, in that order). Never build an `EmailMultiAlternatives` directly from outside this module — the preference check, viral CTA, footer and logo attachment would all be bypassed.

### `invitation_service.py` — Sending an invitation, and the member-proposal flow

**`deliver_invitation(collection, email, inviter_name, quota_user_code=None, proposer_name=None)`** is the single place an invitation actually goes out: the `get_or_create`, the RSVP pair, the email and the daily quota. Both callers reach it — the owner inviting directly (`CollectionInviteView`) and an owner approving a member's recommendation — so an approved proposal is indistinguishable from an owner's own invite. **The founder counts as already inside** (`is_owner` or `is_invited` → `(user, True)` before any RSVP, email or quota): they are an FK, never an `invites` row, so the callers answer their usual "already invited". Two paths would drift, and the one used less often is the one that would rot. (The bulk-invite endpoint keeps its own batched fan-out: it creates RSVPs in a batch and mails off the request thread, a different shape.)

**One invitation per person.** Before anything is created, `deliver_invitation` asks `invitation_blocked(collection, email, inviter_code)`: an address that this collection's founder or the inviter has already invited (`InvitationRecord` `SENT` or `DECLINED`) raises `InvitationAlreadyAsked` (no argument: the address must not reach logs or error reports), so no `User`, RSVP, email or quota spend exists for it. Somebody already inside is answered first with the usual `(user, True)`. `inviter_code` is `quota_user_code`, or the group's owner when none is given. It clears the pending pair of that user and collection before minting a fresh one: not a resend, but the case where the record went `ACCEPTED` by joining another group of the same founder while this group's invitation was still waiting. On a send it writes the record (`record_invitation`, before the email leaves); `resolve_invitation` moves it to `ACCEPTED` (`_join_collection`) or `DECLINED` (the decline link). `proposal_approval_blocked` returns the same refusal (`invite_already_asked`, 400) for the owner's two routes. The email's `invite_source_note` tells the invited person this, in three languages. Records and their retention: [`InvitationRecord`](../models/CLAUDE.md#invitationrecord).

The **daily invitation-email quota** helpers live here too (`_invite_quota_left`, `_consume_invite_quota`) — they moved out of the views when both senders ended up here, since a service reaching back into a view for them was a layering inversion. The views import them.

| Function | Behaviour |
|---|---|
| `proposal_team(collection, proposer=None)` | The people a recommendation is put to: the founder first, then every co-curator, minus the one recommending and anyone with no address. Any of them may decide, so the question goes to all of them, as a hold request goes to everyone who runs the thing. |
| `create_proposal(collection, proposer, email, note="")` | Records the suggestion and, **for each curator of `proposal_team`**, mints their **own** approve/reject RSVP pair, writes their own `INVITE_PROPOSED` (the payload carries `collection_code` and `proposal_code`) and emails them in their own language (`_recipient`: their preference, else the group's). Returns the founder's pair. **Nothing reaches the proposed address** — no `User` row, no email. If the answer turns out to be no, that person must never learn they were suggested. |
| `clear_proposal_traces(proposal)` | Takes a decided suggestion off every desk: deletes every `INVITE_PROPOSED` whose `payload.proposal_code` is the suggestion's (for **all** curators, not the one who decided) and every approve/reject RSVP minted for it. Called at the end of `approve_proposal` and `reject_proposal`, so the in-app route and the emailed link settle it the same way. |
| `proposal_approval_blocked(proposal)` | `(message, http_status)` if this approval cannot be delivered — the owner's daily quota (429) or the collection's member ceiling (400) — else `None`. **Shared by the owner's two routes**, the in-app POST and the emailed approve link, which used to differ: the link approved unconditionally, making `INVITE_EMAILS_PER_DAY` walkable one recommendation at a time. Someone already in the group is excluded from the ceiling check — an approval that adds nobody must not be refused. |
| `invitation_acceptance(days=30, settle_days=7)` | How each account's invitations were answered, for a deployment's report (no view, no endpoint). Over the `InvitationRecord` rows sent between `days` and `settle_days` ago (both ends included), grouped by **`inviter`** (whoever spent the quota, not whose group it was), returns `[{"inviter", "sent", "accepted", "declined", "unanswered"}]`, most sent first. Anything sent in the last `settle_days` is left out so that somebody who has just sent a batch does not look like a spammer. It only measures: **nobody is stopped or blocked by it**. |
| `approve_proposal(proposal)` | **Reserves the decision first** (a conditional `UPDATE … WHERE status = PENDING` inside `transaction.atomic()`; `ProposalAlreadyDecided` and nothing sent when another curator already settled it, so two curators answering at once cannot both act), then delivers the real invitation via `deliver_invitation` (and clears the suggestion's traces), charged to the **owner's** quota (the mail leaves their group under the deployment's domain) and naming the proposer in the body — the invitee almost certainly knows *them*, not the owner. Bare `name`, never `display_name`: the fallback is the email address and this message goes to a third party. |
| `reject_proposal(proposal)` | Reserves the decision first like approve (`ProposalAlreadyDecided`, nothing sent, if another curator got there), marks it rejected, clears the suggestion's traces and tells the **proposer** — in-app and by email, **with no reason**. Silence would leave them waiting and asking again; a reason would put words in the owner's mouth about rules that are not the product's business. The proposed person is never contacted. |

### `join_quota.py` — The daily cap on the door that needs no account

`POST /auth/join/` mails a magic link to whatever address is typed into it, and **neither door that reaches it is a secret**: a PUBLIC collection's `collection_code` is printed in that collection's own URL, and a share token exists to be passed around. So without a cap, anyone may ask a deployment to send mail to anyone — a relay pointed at the operator's own sending domain, ending in complaints against it and genuine magic links landing in spam.

**The two signed-in doors count against the same cap** (`CollectionJoinView`, and `ShareJoinView` — `POST /share/{token}/join/`, added 2026-09-29): they send no mail, but a ceiling that only stopped strangers would be one anyone with an account could walk around, and each asks `join_quota_exhausted()` before joining and calls `consume_join_quota()` after.

The view's own rate limits never closed this and were not meant to: they cap how often **one IP** asks (5/min) and how often **one victim** is mailed (5/hour), which says nothing about a hundred IPs mailing a hundred different strangers once each. `INVITE_EMAILS_PER_DAY` did not either — it counts what an *account* sends through the owner's invite routes, and this is the one door with no account behind it.

| Function | Behaviour |
|---|---|
| `join_quota_exhausted(collection_code)` | Whether this collection has already taken today's joins. `False` when the cap is off. Checked in `JoinView` **after** the target resolves and **before** anything is created, so a refusal leaves no `User`, no RSVP and no mail. Not asked for an address already in the group (founder, co-curator, member): the cap stops mail to strangers, and they are only coming back in. |
| `consume_join_quota(collection_code)` | Records one join against today's allowance. Called after the send is dispatched, so a join that failed earlier costs the collection nothing; a send to someone already in the group is not charged. |

**Keyed per collection, deliberately.** Per IP is what already failed. Per *deployment* would be worse than nothing here: one abused collection would deny every other collection its joins, handing the attacker a denial of service against the whole instance in the name of stopping a relay. Per collection, abusing a group's public code costs that group its own day.

**Off unless the operator sets `COLLECTION_JOINS_PER_DAY`**, like every other abuse guard — and for the usual reason plus one of its own: a share link pasted into a group chat can legitimately bring in two hundred people in an evening, which upstream has no business calling abuse. It follows `RATELIMIT_ENABLE` (the same switch as the invitation quota, so an operator turning limits off does not have to find two places to do it), and shares the DatabaseCache read-then-set non-atomicity note — a burst can slip a few past the line, which is the right trade for coarse reputation protection. **It survives only as long as the shared cache keeps it**: both daily allowances (`joinq:` here, `invq:` for invitations) sort ahead of the limiter windows (`rl:`) in the cull DatabaseCache runs past `MAX_ENTRIES`, so with Django's default of 300 a few hundred client IPs inside a minute erased them (measured 2026-09-29). `CACHES['default']` sets `MAX_ENTRIES` to 20,000 for that reason — `test_shared_cache.py` pins it through a real burst on `/health/`.

A refusal returns the endpoint's **unified response** and writes a `security` warning. It cannot say why: "over its limit" would confirm that the token or code names a real, joinable collection, which is exactly what that response exists to withhold. The operator is told instead — the same shape as the capacity alarms, where the tripwire reports to whoever set it and never to whoever tripped it.

Each join sends one magic link, and a **first** join also sends the collection's welcome document when the owner set one, so the mail this permits is at most twice the configured number. It caps joins because that is the event worth counting; the emails follow from it.

### `creator_policy.py` — Who May Create What, On This Deployment

The one place a deployment says whether an account is enough to open a collection in either mode and offer a thing under any of the verbs. Upstream the answer is **yes, to everyone, always** — `OpenCreatorPolicy`, the default of the `CREATOR_POLICY` setting — so a standalone checkout has no gate and behaves exactly as it did before this module existed. A deployment with a narrower rule (only the board opens COMMUNITY collections; lending is vetted first) points the setting at its own subclass instead of editing the serializers, and nothing about that rule needs to live in this repository.

It answers only *may this person bring such a thing into existence here at all*. It is **not** object-level permission (`IsCollectionOwner`), and **not** the owner's per-collection `allowed_thing_types` allowlist (`core.views._helpers.type_validity_error`).

| Function / class | Behaviour |
|---|---|
| `Capabilities` | Frozen dataclass: `collection_modes`, `thing_types`, `request_url`, `co_owners_enabled`, plus the derived property **`collection_kinds`** — the kinds with at least one verb in `thing_types`, which a policy never declares (so no deployment's class has to know about kinds). Its `as_dict()` serves `collection_kinds` too. `as_dict()` is the JSON shape served on `GET /auth/me/` (lists, not tuples). `request_url` is where to go and ask; `None` means there is nowhere, which is the standalone's answer because there is nothing to ask for. `co_owners_enabled` (default `True`) is whether this deployment lets a collection's curators promote a member to co-curator at all (either mode, since 2026-09) — see `co_owners_denial` below. |
| `CreatorPolicy` | Base class. A subclass overrides **`capabilities(user)`** and nothing else; `allows_collection_mode()` / `allows_thing_type()` are derived from it, so a policy cannot allow something it does not advertise. Instances are cached and shared across requests — subclasses must be **stateless**. |
| `OpenCreatorPolicy` | The default. Every mode, every verb, no request URL. Its two lists come from `Collection.Mode.values` / `Thing.Type.values` rather than being spelled out, so a verb added to the model is available the day it is added — **RESERVE_THING included**: it is a full product feature upstream (a self-hoster gets it for all their users). An operator running OIUEEI as a service typically gates it, which a deployment can do for free by leaving it out of its own policy's set of open types — no policy code, RESERVE just isn't in the "before vetting" set. |
| `get_creator_policy()` | The configured policy, instantiated once **per dotted path** (`lru_cache` under the setting lookup, not over it — a module global would pin whichever policy the process loaded first, and `override_settings` in a test would silently not apply). |
| `capabilities_for(user)` | This deployment's answer for one user — the single way to ask, used by both denial helpers and by `MeView`. **Not cached**: a caller in a loop must hoist it and pass it down (see `ThingBulkCreateView`). |
| `collection_mode_denial(user, mode, capabilities=None)` | The message explaining why this deployment refuses that mode, else `None`. |
| `collection_kind_denial(user, kind, capabilities=None)` | The same for a kind of collection (a stall, a library, a shed): refused when none of its verbs is in `thing_types`. Enforced in `CollectionViewSet.perform_create` only — a kind never changes, so there is no second door. |
| `thing_type_denial(user, thing_type, capabilities=None)` | The same for a verb, in prose (`"a lend thing"`, not `LEND_THING`) — the text reaches an API client as the 403 body. Answers the **personal** question only. |
| `community_contribution_types(collection, user)` | The set of thing types `user` may add to `collection` **despite** `thing_type_denial()` — empty unless they are an invited member of a COMMUNITY collection whose owner has explicitly named the type in `allowed_thing_types`. See "Initiating vs. contributing" below. Empty for a non-member, the owner, a PROPRIETARY collection, and `None` (and for an empty list, which only a hand-edited row can hold — the list is always explicit). **`RESERVE_THING` is always subtracted** — a reservations collection is PROPRIETARY by rule, so a COMMUNITY allowlist naming it can only be a hand-edited row, and a member must never inherit it. |
| `co_owners_denial(user, capabilities=None)` | Why this deployment won't let `user` promote a co-curator, else `None`. Same shape as the two denials above — enforced at the one door that creates co-curator status, `CollectionCoOwnerView.post`. **Grandfathered like every other capability here**: it gates *promoting*, never *demoting* — a curator can always undo a co-curator already appointed, even on a deployment that has since disabled the feature. |

**A policy is consulted exactly once per decision.** Both helpers resolve `capabilities()` a single time and read the allowed list *and* the `request_url` off it — the refusal needs both, and asking twice used to make every denial cost double. Both also accept an already-resolved `capabilities=`, which is how `ThingBulkCreateView` judges up to 100 CSV rows with one evaluation instead of 100: the verb is per row, whether this deployment offers it is not. `CreatorPolicy` requires subclasses to be **stateless, not cheap** — the policies this setting exists for are the ones that go and look something up — so the call count is part of the contract, pinned by `TestThePolicyIsConsultedOnce`.

**The module stays free of HTTP**, like `booking_service`: it returns a message and the call site raises the 403. The message carries the request URL when the policy has one, because the API is usable without the SPA and a client that only ever sees the refusal would never learn that asking is possible.

#### Where it is enforced (five doors, not two)

| Call site | Refuses |
|---|---|
| `CollectionViewSet.perform_create` | The mode, **including the PROPRIETARY default** when the body names none |
| `CollectionViewSet.perform_update` | Switching an existing collection **into** a withheld mode |
| `ThingViewSet.perform_create` | The verb, unless it is a COMMUNITY contribution (below). The collection is resolved first now, but a nonexistent or un-addable one still falls through to the **same 403** as no collection at all — the verb refusal never turns on which collection was named |
| `ThingViewSet.perform_update` | Moving a thing **into** a withheld verb — unless every collection it sits in is a COMMUNITY contribution that allows the new one |
| `ThingBulkCreateView` | The verb of each CSV row — as a **row error (400)**, like the collection's own allowlist, since that endpoint's contract is that one response names every bad row. The COMMUNITY exception is resolved once for the whole batch |

**Initiating vs. contributing.** A `CreatorPolicy` gates *initiating* — opening a collection, or offering a verb under your own name or into your own collection. It does **not** gate a member adding a thing to a COMMUNITY collection they were invited to, of a type that group's owner has explicitly put in `allowed_thing_types`. That owner is the vetted party (a deployment narrow enough to hold COMMUNITY creation behind a request vetted *them*), and the allowlist is them opening their group to that verb. `community_contribution_types()` is the single definition; the three thing-creation doors gate on `thing_type in community_contribution_types(...)` before raising. The allowlist is always explicit — the verbs within the group's kind, never empty — so it is the owner's choice, made at creation: both verbs when members may set a price, only the free one when they may not. An empty list (a hand-edited row) grants nothing. Upstream (`OpenCreatorPolicy`) the whole branch is dead: every verb is allowed, so `thing_type_denial()` returns `None` first. Pinned by `test_creator_policy_gate.py`.

**The two edit paths only judge a change.** A collection already in a mode (or a thing already under a verb) the policy has since stopped handing out stays fully editable by its owner: the gate is on bringing that state into existence, never on living in it, so narrowing a deployment cannot freeze what people already own.

**`GET /auth/me/` serves the same `capabilities()`** the doors refuse with (see `MeView`), which is what keeps the UI from offering a control that 403s when pressed.

### `account_service.py` — Account Erasure (Right to Be Forgotten)

One function, `delete_account(user)`: a `user.delete()` inside `transaction.atomic()` plus a security-log line, returning the (now dangling) user code. The module exists because the *erasure map* deserves one written-down home — the schema already encodes it: collections/things/bookings/RSVPs/notifications/daily-activity/invitation records (as founder or inviter) **cascade**; FAQ questions and ThingTransfer hops on other people's things **survive with the user FK nulled** (SET_NULL — content stays, attribution goes, rendered as "former member"); `Report` rows were already SET_NULL; the `Event` log holds only code snapshots (never exposed), and the erasure writes into it — inside `deleting_as(user)` — a `COLLECTION_DELETED` per collection, a `THING_REMOVED` per thing and a `MEMBER_LEFT` per membership, from the receivers in `deletion_events.py`; stored files are deleted by the `asset_cleanup` `post_delete` handlers, which fire for cascade-deleted rows too. Called only from `VerifyLinkView._handle_account_delete` (the emailed-link commit step).

### `export_service.py` — Data Portability (Right to a Copy)

The mirror of `account_service`: *what dies with you is what you get to take with you*. Read the two docstrings together — when a new model arrives, both are wrong until both are updated.

#### Public API

| Function | Returns |
|----------|---------|
| `build_account_export(user)` | The whole of one person's data as a JSON-serialisable tree: `_manifest`, `_readme`, `profile`, `collections_owned`, `collections_member_of`, `things`, `bookings`, `faqs`, `proposals_made`, `transfers`, `notifications`, `reports_filed`, `activity`. One private helper per key, each with its own `select_related`/`prefetch_related`. |
| `build_collection_export(collection)` | An **operational** copy of a group, other members' things included: `collection`, `members`, `pending_invitations`, `proposals`, `things`, `bookings`, `faqs`, `transfers`, `stats`. Not art. 20 and doesn't pretend to be — it is what makes a library of things portable. **Curator-only (owner or co-curator); the caller enforces that** (`require_collection_curator`), this function trusts it. **`bookings` and `faqs` stay inside the group outside PROPRIETARY** (2026-09-29, `_group_people`): a thing can sit in two groups and a booking records who asked, not through which one, so a COMMUNITY copy keeps a request only when its requester is the owner or an invited member, and a question when it is visible (its author shows to anyone who sees the thing) or its questioner is one of those people — a hidden question of a deleted account (`questioner` NULL) is out. The people are one `values_list` for the whole file, never an `is_invited` per row, and the file is the same whichever curator downloads it (the function takes no user). PROPRIETARY is unchanged: its curators manage every thing and the app already shows them everything. `transfers` (the journey names names to anyone signed in who sees the thing) and `stats` (counts) are untouched. | `export_bytes(payload)` | `json.dumps(..., ensure_ascii=False, indent=2, default=str)` encoded UTF-8. `default=str` is the safety net, not the plan: every builder already returns JSON-native values, so a type reaching it means a new column arrived without a decision. |
| `export_filename(code)` | `oiueei-ABC123-2026-08-21.json` — the code says which copy, the date says when it stopped being true. |
| `collection_stats_rows(collection)` | `[(metric, value)]` — **the** definition of every usage metric, rendered two ways: `CollectionStatsView` writes it as CSV, the collection export carries it as a dict under `stats`. Public despite living among the private helpers, because a view in another module imports it. `STATS_WINDOW_DAYS` (90) is the window every `(90d)` metric measures. |

The catalogue is `README_TEXTS` (en/es/ca), kept in parity by a test, and it exists because a JSON tree can't explain its own omissions: someone who finds no reports about their things should learn *here* that they are anonymous by design, not conclude the export is broken.

#### What never leaves — each pinned by a test, most against the raw bytes

| Omission | Why |
|----------|-----|
| `Collection.share_token`, every `RSVP.token` | A file gets forwarded; a token inside it is a group — or an account — forwarded with it. |
| Co-members' emails from groups the exporter merely **joined** | Member emails ride along only in collections they **own**, which is the roster the guests page already shows them. |
| `age_range` / `postal_code` of anyone else, unless the group is COMMUNITY | Built by `Collection.owner_member_rows`, the **same** row shape `CollectionSerializer.get_invites` serves the guests page — one definition, so the export cannot be the back door to what the API withholds. It used to be a second copy of that loop, kept true by vigilance. *(The aggregate breakdown inside `stats` is a different thing and stays: it is the stats CSV, which any collection owner can already download — and which names a bracket or a postal code only when at least three members share it, so a small group's figures are not one person's.)* |
| Reports **about** the exporter's things (both exports) | Reporting is anonymous by design; the export must not become the leak the notification avoids. |
| `BookingPeriod.requester_email`, third parties' demographics, other members' notifications and activity | Third-party data with no reason to be in this file — a counterpart is a code and a public name. |
| In a non-PROPRIETARY group's copy: requests and **hidden** questions from people outside the group | They concern a member's thing, which the organiser does not manage (`Thing.can_manage` wants PROPRIETARY); only whoever runs that thing sees them in the app. A person is inside the group when they are its owner or in `invites` (`_group_people`). |
| The `deal` M2M, `password`, `is_staff`/`is_superuser`, the `*_alarm_sent` / `capacity_unblocked` flags | Not the person's content: the first is third parties, the last is this deployment's moderation ledger. |

**Photos and the welcome PDF travel as URLs, not bytes.** It keeps the response inside Heroku's 30-second window — and it is why the page offering the download has to say that deleting the account breaks those links.

### `calendar_export_service.py` — The Collection Calendar (.ics)

A curator downloads their collection's upcoming **date-based** reservations (LEND / RENT / RESERVE) as an **RFC 5545 VCALENDAR** (`.ics`). A whole-day booking (LEND/RENT, `DAY`-unit RESERVE) is **one all-day event that spans its block** — pickup day to return day. An **`HOUR`-unit RESERVE_THING** (`booking.start_time` set) is instead one *timed* event, rendered in UTC. Consumed only by `CollectionCalendarExportView` (POST) and the front end's `useCalendarExport` hook, behind the collection menu's calendar entry on the collection page (through `useCollectionDownloads`).

**Why `.ics` and not the CSV this was until 2026-09-28.** The CSV shipped `Start Date`/`End Date` as `MM/DD/YYYY` on the documented claim that Google Calendar's importer parses that format "regardless of account locale". That claim was never true: the importer reads dates in the **importing account's own locale**, and it was only ever verified against a US-locale account (2026-09-10). In production, an early adopter's day/month account imported a reservation dated `10/01/2026` (meant as 1 October) as **10 January** — the exact kind of misread a plain string of digits can't defend against. iCalendar's `DTSTART`/`DTEND` are unambiguous (`YYYYMMDD` or `YYYYMMDDTHHMMSSZ`) and carry their own timezone; Google, Apple Calendar and Outlook all import it, and on a phone opening the file is enough — no importer dialog with its own date-format assumption stands between the file and the calendar.

| Function | Returns |
|---|---|
| `build_calendar_export(collection, user=None)` | `(ics_bytes, count, cancelled)`. Renders **every upcoming reservation** the downloader may see (below), every call — see "No more incremental watermark" below — plus every upcoming one **cancelled** since it was confirmed (see "Cancellations" below). `count` is how many confirmed `VEVENT`s the file holds, `cancelled` how many cancellations ride along (both `0` ⇒ nothing to import; the SPA then offers no download). Copy speaks `resolve_email_language(user, collection)` — the downloading curator's language, then the group's, then `EMAIL_LANGUAGE`. |
| `calendar_filename(code)` | `ABC123-calendar.ics` — the stats CSV's shape, the iCalendar extension. |

**Which reservations.** `status == ACCEPTED` — or `CANCELLED` on a `RESERVE_THING` — with `thing_type in DATE_BASED_TYPES`, `end_date >= today` (upcoming **or in progress**), the thing sits in this collection. Ordered by `start_date`.

**Whose reservations (the app's rule).** In a **PROPRIETARY** collection the curator gets all of them (its curators run every thing). In a **COMMUNITY** collection only those of things the downloader **owns** (`thing_code__owner=user`, asked in the query — `Thing.can_manage` is just the owner there), and **none when no `user` is given**: the names of whoever asks for another member's thing are not a COMMUNITY curator's to read, in `/owner-bookings` or on the thing's calendar, so they are not in the file either. The view's permission (curators only) and the file's format are unchanged.

**Cancellations (2026-09-29).** The file is a copy, not a subscription, so a calendar that imported a reservation kept it after it was cancelled. Every download now also carries each upcoming reservation cancelled after it was confirmed, under **the same `UID`**, with `STATUS:CANCELLED` and `SEQUENCE:1` — confirmed events are `STATUS:CONFIRMED`, `SEQUENCE:0` — since RFC 5545 has a calendar accept a revision only when its `SEQUENCE` is higher than the copy it holds; an app that honours the status then drops or strikes out its copy. Only `RESERVE_THING` qualifies: it is the one verb that goes `ACCEPTED → CANCELLED` (`cancel_reservation`); a loan or rental is only ever cancelled while `PENDING` (`cancel_booking`), so it never reached a calendar. **How each app treats a cancellation received by file is the app's call and was not verified from here** — the file says what the standard lets it say. The view reports the count in `X-Calendar-Cancelled`, so the SPA still downloads a file that holds nothing but cancellations.

**No more incremental watermark.** Every `VEVENT`'s `UID` is `{booking.code}@oiueei` — stable across downloads, so a calendar app that re-imports the file updates its own copy of an event in place instead of duplicating it. That is what made the old per-`(collection, booking)` watermark (`CalendarExportMark`) unnecessary: the app doing the deduplication is the one that actually knows what it already has. The model and its table are gone (see [`CalendarExportMark`](../models/CLAUDE.md#calendarexportmark-leaving-the-schema)). The watermark's old failure mode is also gone: a curator whose import failed used to be locked out of re-downloading the same reservations; now a second attempt just works.

**Dates — whole-day events.** `DTSTART;VALUE=DATE` / `DTEND;VALUE=DATE` map **straight** from `booking.start_date` / `booking.end_date` — iCalendar's all-day `DTEND` is **exclusive**, exactly OIUEEI's own `end_date` (the day the thing is free again for the next booking, matches `has_overlap`). So a one-week loan picked up Monday the 14th (`end_date` the 21st) blocks the 14th–20th and leaves the 21st open; a 3-day reservation (`end_date` = start + 3) blocks all three days. Do **not** subtract a day. Dates *inside* the `DESCRIPTION` still render `DD/MM/YYYY` like everywhere else a person reads a date (`_ddmy`).

**Dates and times — an `HOUR`-unit event.** `booking.start_time`/`end_time` set means the event is *timed*: `DTSTART`/`DTEND` are rendered in **UTC** (`_utc`, reading the wall-clock time in `settings.TIME_ZONE` — the zone `opening_hours` and every reservation time are written in — then converting), which is what lets the file carry no `VTIMEZONE` and still land on the right wall clock in every importing calendar, on both sides of a DST change. And — the trap the CSV also had to guard — the day is **`start_date`, never `end_date`**: for an `HOUR`-unit booking `end_date` is only the day-based "free again" marker every other consumer (reminders, `close_transfers`, this module's own upcoming-reservations filter) reads; using it would push every hourly event a day late. `test_calendar_export_service.py`'s `TestHourlyReservation` pins both the whole-day and the hourly shape side by side, and the exact production bug (1 October, Europe/Madrid, 17:00–21:00 → `20261001T150000Z`/`20261001T190000Z`) by name.

**RFC 5545 shape.** Every physical line ends `\r\n`; a line over 75 *octets* (bytes, never characters) folds onto a continuation that starts with a single space — the fold marker itself, which `_fold` must actually write (not merely budget room for: an earlier version of this function reserved the octet but never wrote the space, which silently ate the continuation's first real character on every unfold — found reading a folded headline back). A `TEXT` value (`SUMMARY`, `DESCRIPTION`, `LOCATION`) is escaped per RFC 5545 §3.3.11 — `\`, `;`, `,` and a line break become `\\`, `\;`, `\,` and literal `\n` — which is the escaping this format needs; there is no equivalent of the CSV's spreadsheet-formula guard, since nothing downstream evaluates a calendar entry as an expression. Localized headlines (`{"es": …, "ca": …}`) resolve to the reader's language via `resolve_localized`. A member with no display name is `"a member"` / `"un miembro"` / `"un membre"` — never a blank, never their email.

**The title says the thing and the person, the description says what kind** (`subject_*` is `{thing} → {person}` for a loan and a rental and `{thing} — {person}` for a reservation; `kind_*`, "Loan" / "Rental" / "Reservation" in the three languages, is the first words of `DESCRIPTION`). A library that holds both loans and rentals could not tell them apart by a title that carried the kind, and the kind in front of every title is noise in a calendar that is already about one group's reservations. `UID` and `SEQUENCE` do not depend on it: a cancellation still revises the event it cancels.

`CALENDAR_TEXTS` (en/es/ca) is an inline catalogue like `export_service.README_TEXTS`, kept in parity by `test_calendar_export_service.py` — it's a file for a machine, not a message, so it stays out of `email_texts/`.

### `membership_service.py` — Ending a Membership

`end_membership(collection, user, *, actor)` is the one place a person leaves `invites`: inside `transaction.atomic()` and `deleting_as(actor)` it deletes every `Thing` the user owns in the collection (`things_leaving_with`: any status, both modes, so each `THING_REMOVED` names who acted), then removes them from `invites` and `co_owners`, and returns how many things went. **It raises `ValueError` for the founder** (an FK, never a member: their things are not the member rule's to delete) before touching anything. A thing lives in one collection and its owner always has access to it, so the things go with the person. Running activity does not hold the deletion back; the live requests and reservations (`BookingPeriod.blocking_filter`) are read first, and on commit one `send_thing_left_with_owner_email` goes to each requester — once per requester and thing, never to the leaving member, and nothing if the transaction rolls back. Used by `CollectionLeaveView` and the accepted-member branch of `CollectionInviteView` DELETE; demotion (`CollectionCoOwnerView`) and the pending-invitation branch do not call it, and account erasure already deletes by CASCADE.

`delete_thing(thing, *, actor)` is the same read-then-notify for deleting a single thing (`ThingViewSet.perform_destroy`): `people_told_on_delete` lists who is told, the thing goes, and on commit each is emailed with `send_thing_withdrawn_email`. It never blocks the delete.

**In a network**, a dinamizador who stops being one takes the role's weight with them. `demote_curator(collection, user, *, actor)` (demotion) and `end_membership` (removal or leaving) delete their things **and their `NetworkPoint`** in the same transaction, and email whoever had a live request on one of those things once it commits. `network_exit_block(collection, user, *, removing)` is what says no first: it returns `("curator_things_lent_out", headlines)` while one of their things is out (an accepted loan or rental that has started and has not reached its end date: there is no "returned" state), and — when removing, which also ends what they hold themselves — `("member_holds_loans", headlines)` while they have a started loan in hand; `None` outside a network. Erasing an account is never blocked (the cascade also takes the point), and tells whoever held a thing the way a member leaving does.

### `deletion_events.py` — Log a Deletion Whichever Way the Row Goes

`post_delete` receivers on `Collection` (→ `COLLECTION_DELETED`) and `Thing` (→ `THING_REMOVED`, with its type) and a `pre_delete` receiver on `User` (→ one `MEMBER_LEFT` per membership; the M2M rows still exist then), registered in `core.apps.CoreConfig.ready`. They fire for every path — the API, the admin, the cascade of an account erasure, the retention purge, a `QuerySet.delete()` — and write inside the delete's transaction (never `on_commit`), so a rollback leaves no event. The actor is a `ContextVar` set by `deleting_as(user)` (the two viewsets' `perform_destroy` and `delete_account` use it) and blank outside one. `deletion_events_suppressed()` records nothing; `seed_demo --reset` runs under it because the demo is not history. A view never calls `Event.log` for a delete.

### `asset_cleanup.py` — Delete Stored Files on Delete, and When a Save Drops One

Frees the stored objects a record owns when the record itself is deleted, **and the object a save drops** (a removed profile photo, a swapped cover, a photo taken out of a gallery, a replaced welcome PDF), so neither leaves orphaned files piling up (storage cost + clutter, and the `/legal` promise that a photo goes when you remove it). The bucket has no notion of a foreign key, so nothing else would ever notice they had become unreachable.

#### How it's wired

- **`post_delete` signal handlers** on `Thing`, `Collection` and `User` (registered in `core.apps.CoreConfig.ready`). Django fires `post_delete` for cascade-deleted rows too, so this single hook covers every path: a direct thing/collection delete, the collection view's orphan-thing sweep (`CollectionViewSet.perform_destroy`), and a user-account FK cascade (which removes their collections and things).
- **Runs on `transaction.on_commit`** — a delete that rolls back keeps its images. The destroy **never raises** (`_destroy` swallows + logs): an orphaned asset is a smaller problem than a delete that blows up.

#### What gets destroyed per model

| Model | Assets |
|-------|--------|
| `Thing` | `thumbnail` and every `gallery` id |
| `Collection` | `thumbnail`, `welcome_doc` (the welcome PDF — also `resource_type=image`, so the default destroy kwargs are right) |
| `User` | `photo` |

#### A save that drops a key destroys it (2026-10-02)

Until 2026-10-02 only a delete freed anything: a replaced or removed photo stayed in the bucket until someone ran `cleanup_orphan_images` by hand inside its 30-day window, and past that window, for good. Now a **`post_init`** handler notes the keys each row was loaded with (`instance._stored_assets`) and a **`post_save`** handler destroys the ones the save dropped — on commit, under the same rules as a delete (seed keys spared, a key another row holds kept, never raises, `suspended()` honoured). Three details carry the weight:

- **A deferred column is never read.** `.only()` / `.defer()` leave a column out of `instance.__dict__`, and remembering it would cost a query per row; a column the handler never saw is simply one it cannot say a save replaced. Pinned with `django_assert_num_queries`.
- **`update_fields` is honoured.** A column left out of it was not written, so it neither drops a key nor becomes the new baseline — the next real write drops the key the row actually held.
- **The remembered keys are a copy**, so `thing.gallery.remove(k); thing.save()` still reads as a change.

**Left open on purpose:** two requests that both load a row and save it in full can race — the first replaces a key and destroys the old object, the second writes the old key back, and the row names an object that is gone (a broken photo, the same lost update a concurrent full save already causes to every other column). Closing it would mean locking every edit of a thing, collection or profile; re-uploading the photo mends it.

Anything that bypasses `save()` (`QuerySet.update`, `bulk_update`) bypasses this too — none writes an asset column today. What it misses is left for the orphan sweep, which is the net, not the mechanism.

#### A key another record still holds is never destroyed (2026-10-02)

A row does not own its keys. A key is the path of its photo's public URL, and `ImageIdField` binds it to a **folder**, not to an uploader — so anyone who can see a photo can save its key on a thing of their own. Until 2026-10-02, deleting that thing deleted the photo for its real owner too. `_destroy` now asks **`is_referenced(key)`** first, at destroy time (after the commit, so the row being deleted no longer counts), and keeps a key any row still holds. The gallery is a JSON list and SQLite has no JSON containment lookup, so the check matches the list's text (`icontains`) on every backend and confirms on the decoded list — a longer key that merely starts with this one does not count.

**One table of key-holding columns, `ASSET_FIELDS`** (`Thing`: thumbnail, gallery · `Collection`: thumbnail, welcome_doc · `User`: photo). The delete handler, `is_referenced` and the orphan sweep (`cleanup_orphan_images`, via `referenced_keys()`) all read it: a column missing from one hand-written copy is a live photo deleted.

#### The seed pool is never destroyed

Keys under **`storage.SEED_PREFIX`** (`oiueei/seed/`) are skipped outright. The demo's fixtures are a *shared, static pool*: every database that has ever run `seed_demo` points at the same objects, so they don't belong to the rows that reference them and one delete must not take them from every other environment.

The skip is **per key, not per record** — a genuine upload sitting in the same thing's gallery as a seed image is still cleaned.

This used to be handled only by `seed_demo --reset` suspending the mechanism, which left every *other* door open: the Django admin, an FK cascade, a shell delete. Deleting the demo from the admin emptied the whole folder for real, which is what prompted the guard. `cleanup_orphan_images` already skipped the same prefix — the two now read it from one constant in `storage`, because two hand-written copies of a path that must agree are one edit away from a demo that deletes its own photographs.

#### Suspension (still needed, for a different job)

`suspended()` is a context manager that disables the cleanup entirely for deletes inside the block. **`seed_demo._reset()` still wraps its deletes in it** — belt and braces over the skip above, and the reusable guard for any bulk delete that must not touch the bucket at all.
