# Serializers Documentation

All serializers live in `core/serializers/` and are re-exported via `__init__.py` for flat imports (`from core.serializers import ThingSerializer`).

---

## Patterns

### Naming Convention

Each domain module follows a consistent set of serializer roles:

| Suffix | Purpose | Example |
|--------|---------|---------|
| `Serializer` | Full read representation | `ThingSerializer`, `CollectionSerializer` |
| `CreateSerializer` | Validated input for creation | `ThingCreateSerializer` |
| `UpdateSerializer` | Validated input for partial updates | `ThingUpdateSerializer` |
| (action name) | Single-purpose input | `CollectionInviteSerializer`, `FAQAnswerSerializer` |

### Security Fields (`core/validators.py` and `core/serializers/thing.py`)

All user-facing text inputs use custom validator fields to prevent XSS:

| Field | Validates | Used for |
|-------|-----------|----------|
| `SafeHeadlineField` | Rejects HTML tags (regex), unsafe link schemes and line breaks | FAQ questions, location, name, postal code, User headline |
| `SafeTextField` | Rejects HTML tags (regex) and unsafe link schemes; line breaks allowed (Markdown) | FAQ answers, pause message, broadcast message, User `about` |
| `LocalizedHeadlineField` | Everything `SafeHeadlineField` does, **plus** mode-awareness: the value may be an inline `{lang: text}` map (see below) | Thing/Collection `headline`, each `tags` label |
| `LocalizedTextField` | Everything `SafeTextField` does, plus mode-awareness. Thing/Collection `description` (2000/lang, `TextField` column) + Collection `deposit_policy` (256/lang) | Thing/Collection `description`, Collection `deposit_policy` |
| `ImageIdField` | Alphanumeric + `_-./` only, no leading/trailing/double slashes, **and the key may not name one of the *other* asset folders** (`folder=` — see below) | Storage keys including their folder path (e.g. `oiueei/things/abc123`) |

### Owner content that carries one text per language

On **Thing and Collection**, `headline`, `description` and each `tags` label may hold one text per language as inline JSON — `{"es": "Las cosas de mamá", "ca": "Les coses de mama"}` — and each reader sees theirs (`core.utils.parse_localized` / `resolve_localized`; the frontend mirrors it in `src/utils/localized.js`). The `Localized*` fields are what enforce it, and the split matters:

- **`max_length` is the limit one language may say** (64 headline / **2000 description** / 32 tag label / 256 `deposit_policy` / 512 `request_info` and `email_note` — what the owner sees in the form counter). It is *not* the column width: the field constructs its base `CharField` with a wider **storage** cap (`LOCALIZED_HEADLINE_STORAGE` = 256, `LOCALIZED_TAG_STORAGE` = 160, `LOCALIZED_DESCRIPTION_STORAGE` = 6400, `LOCALIZED_TEXT_STORAGE` = 1024 for `deposit_policy`), where the same text in all three languages plus the JSON scaffolding fits. **`Thing.description` / `Collection.description` are `TextField`s** — no column limit at all, the serializer's 6400 is just a sanity bound. So **the serializer, not the column, is the guard**.
- **A localized map is validated per language**: each text runs the same HTML / unsafe-scheme (and, for headlines, line-break) rejection a plain value would, and each must fit the visible limit on its own. Three languages don't buy three times the length.
- **Anything that isn't a strict map renders verbatim** — plain prose, a JSON list, an unknown key — so an owner who never uses the trick is never affected by it. A pretty-printed (multi-line) map is rejected for headlines, which flow into email Subject lines.
- **Tag labels stay raw strings end to end**: the subset check (`Thing.tags` ⊆ `Collection.tags`), the case-insensitive dedupe in `_normalize_tags` and the cascade-strip all compare the raw value, so a map is simply one label like any other. Only the *display* resolves.

### The one field with a type rule: `deposit`

`Thing.deposit` is accepted **only on LEND and RENT**. The check lives in `validate_deposit_for_type()` (`core/serializers/thing.py`) and runs from the `validate()` of the create, update and bulk-row serializers, because the JSON API, the edit form and the CSV import are three doors into one column and hiding the input closes only one of them. A RESERVE thing with a deposit is refused by the same check — it is not LEND/RENT, so no new branch was needed. `fee` deliberately has **no** such rule — a price on a gift is merely odd, while a deposit on one is a promise nobody can keep; `fee` is optional everywhere now — the price is what decides the verb, so a gift has none and a sale has one.

**RESERVE_THING has a structural rule instead** (`type_validity_error`, `core/views/_helpers.py`): a RESERVE thing can only be created in a shed (`Collection.is_reservations_collection()`, i.e. `kind == SHED`) — a standalone one, or one aimed at any other collection, is a 400. `normalize_allowed_thing_types(kind, mode, list)` (in `core/serializers/collection.py`) is the other half: it checks a collection's verb list against its kind and writes the list it stores (below).

The rule is stated over the **resulting row**, not the payload: on update, an untouched field keeps its stored value, so a request that changes a loan carrying a deposit into a gift is refused unless it clears the amount in the same breath. Clients that hide the input by type must therefore send `deposit: null` when the type stops being LEND/RENT, rather than omitting it.

### A thing's verb follows its collection's kind and its price

In a collection the **server puts `Thing.type`**: `derive_thing_type(kind, fee)` — a stall gives (no price) or sells (a price > 0), a library lends or rents out, a shed always books. A client may still name a `type`; one its price contradicts is a 400 (`verb_from_price` in `core/views/_helpers.py`: *"In a stall the verb follows the price: with a price it's a sale, without one a gift."*), never silently corrected. The same rule runs for create, edit and every row of the bulk CSV (whose `type` column is optional). An edit that touches the price or the verb puts the verb back in step; one that touches neither leaves it, and **a thing of the other family that a mixed collection kept** at the 0157 migration is never re-derived. The collection's kind is only applied for someone who may add to it, so a refusal never says what kind a private collection is. `type_validity_error` still checks the collection's verb list, with its own message — *"This group doesn't take prices."* — for a paid verb in a COMMUNITY group whose members may not set a price. `ThingCreateSerializer` checks a deposit against the type only when one is named; the view runs the same check on the verb it derives.

### `units`: several identical ones, for a space, a loan or a rental

`Thing.units` (1–20) is read on `ThingSerializer` and the collection's thing summary (with **`units_free_today`**: how many of a loan or rental's units are not out today, `None` otherwise), and accepted by `ThingCreateSerializer` and `ThingUpdateSerializer`. Like the deposit it is judged on the resulting row, from every door: `validate_units_for_type` refuses a number other than 1 on any verb but RESERVE_THING, LEND_THING and RENT_THING (`UNITS_TYPES`; the view runs it again on the verb it derives), and an edit that leaves a thing as anything else puts it back at 1. The CSV import does not take it. **Lowering** `units` is refused while the live requests need more at once (`ThingViewSet.perform_update` locks the row and asks `saturated_periods(live, units + 1)`): a 400 on `units` coded `units_below_booked` with `min` (`requestErrors.units_below_booked`); raising or keeping them is never checked. `BookingPeriodSerializer`, `MyBookingSerializer` and the manager's calendar serializer carry the booking's `quantity`.

### The pause: `paused_from` / `paused_until`

Read on `ThingSerializer` and the collection's thing summary, to anyone who sees the thing, and **`null` once the pause has passed** (`Thing.pause_period`). Written only by `ThingUpdateSerializer` (a thing is not created paused), by whoever may edit the thing (`IsThingManager`); `validate_pause` judges the row that results, and only when the request touches either day: both days or neither, the first not after the last, the last not in the past, at most 365 days (both ends included), and only on a thing with a calendar (`DATE_BASED_TYPES`). Both empty is always allowed, whatever the type.

### Asset URLs

Read serializers expose `thumbnail_url` as a `SerializerMethodField` that calls `core.utils.asset_url()` to convert stored image keys into full object-storage URLs. The raw ID is also exposed (e.g. `thumbnail`) for edit forms.

### Prefetch-Aware Computed Fields

Several `SerializerMethodField`s check for prefetched attributes before falling back to queries:

- `ThingSerializer.get_pending_booking` — checks `obj._pending_bookings` (set by view-level `Prefetch`)
- `ThingSerializer` / `CollectionThingSummarySerializer` `get_available_today` / `get_next_available` — delegate to `Thing.availability_window()`, which reads `obj._blocked_periods` (PENDING+ACCEPTED bookings not already over — `BookingPeriod.blocking_filter` — `Prefetch` set by `ThingViewSet` and by `_optimise_collection_queryset` for collection cards) before falling back to a query, and memoises the result so both fields cost one computation
- `ThingSerializer.get_faqs` / `get_pending_questions` — uses `obj.faq_set.all()` (prefetched)
- `CollectionThingSummarySerializer.get_pending_booking` / `get_pending_questions` — same pattern
- **`get_can_manage`** (both, via `ThingComputedFieldsMixin`) — true for the thing owner, or a curator of a **PROPRIETARY** collection the thing is *read through* (`_reading_collection` — the grid's `parent_collection`, or the thing endpoint's resolved viewable one). Judged against that one collection only, never by walking `collections.all()`: it stays prefetch-safe (`co_owners` is already prefetched for `is_curator`), and the worst it does is hide a control the API still allows — `IsThingManager` re-checks the real `Thing.can_manage` on the mutation. `optimise_thing_queryset(with_collections=True)` adds `collections__co_owners` for the standalone thing endpoints, and the collections come with their curators' pages (`points`, with their users) so a network's pickup point (`point_for` / `card_for`, `display_name`) costs no query per thing.

This avoids N+1 queries when serialising lists of things.

### Foreign Key Exposure

Foreign keys are exposed as 6-character alphanumeric codes, not database IDs:

- `owner = CharField(source="owner_id")` — exposes the FK value directly
- `SlugRelatedField(slug_field="code")` — used for a collection's `theeeme` and for `deal` (M2M)
